# REPORT — AI 회고 보고서

SCRUM-156 초기 프롬프트 실험 모델은 `gpt-6-luna`로 선정한다. 실제 계정 접근 가능 여부와 품질은 실험으로 검증한다. 사용자 제공 `새로운 노트 (1).txt`(48분 59초)를 기준 전사로 사용하며, 기존 68분 강의 파일을 대체한다. 일반·소수 반응·상반 의견·기록 누락/분석 실패의 4가지 실험 입력과 합격 기준은 [실험 시나리오](../experiments/report-scenarios.json)에 정의한다. 가상 청중 기록은 실제 관측값과 구분하며, 원문 파일 전체는 저장소에 복사하지 않는다. JSON 형식·근거 정확성·추측 억제·상반 의견 보존을 필수 평가하고, 대표 샘플 평균 건당 비용 $0.005~$0.01 이하를 목표로 실제 사용량을 측정한다. 이 비용 목표는 보류 중인 입력·출력 토큰 상한을 확정하는 것이 아니다. 초기 모델에서 프롬프트 보완 후에도 품질이 부족하면 동일 샘플로 상위 모델을 비교한다.


### [REPORT-01] AI 회고 보고서 생성 요청

강연방이 `LIVE`에서 `ENDED`로 전환될 때 서버가 방당 보고서 한 건을 `PENDING`으로 자동 접수한다. 강연 중 녹음을 중지하거나 재개해도 보고서는 접수하지 않는다. 강연자가 종료 후 화면을 닫아도 서버에서 작업을 이어가며, 강연자는 별도의 생성 버튼을 누를 필요 없이 이후 상태와 결과를 조회한다.

보고서 화면을 열거나 새로고침할 때는 저장된 상태와 결과만 조회한다. 소유자의 종료된 방에서 보고서가 없다고 확인된 경우에만 ‘보고서 접수하기’를 표시하고, 강사가 눌렀을 때 POST를 보낸다. 조회 연결 실패나 권한 오류는 접수 누락으로 판단하지 않는다.

방 종료가 DB에 저장되면 강사에게 종료 완료를 안내한다. 종료 시 자동 접수가 실패해도 방은 `ENDED`로 유지한다. 누락 여부는 방 상태가 `ENDED`이고 해당 방의 `lecture_reports` 행이 없는지로 판단한다. 서버는 접수 누락 방을 주기적으로 검색하지 않는다. 강사가 ‘보고서 접수하기’를 누르면 서버가 같은 조건을 다시 확인한다. 자동 접수나 다른 탭의 접수가 먼저 성공했다면 기존 보고서의 ID와 상태를 반환한다. 이미 `FAILED`인 보고서에는 버튼을 표시하지 않으며 LLM을 재호출하지 않는다.

수동 최초 접수는 방당 보고서 한 건을 저장하고 `202 Accepted`와 `reportId`, `PENDING` 상태를 반환한다. 자동·수동 접수 모두 마지막 채팅 분석이나 투표 집계가 진행 중이면 그 보고서를 `PENDING`으로 유지한다. 생성에 필요한 기록이 확정되면 서버가 같은 `reportId`를 `PROCESSING`으로 전환해 본문을 생성한다. 강사가 다시 접수할 필요는 없다. 채팅 분석이 `FAILED`로 확정된 구간은 남아 있는 원문을 사용한다.

서버는 보고서 접수가 DB에 반영된 직후와 강연 종료 후 마지막 채팅 분석 결과가 DB에 반영된 직후에 해당 방의 생성 조건을 확인한다. 분석이 먼저 끝났으면 접수 직후에, 접수가 먼저 끝났으면 마지막 분석 결과 저장 직후에 생성을 시작한다. 두 확인이 겹쳐도 같은 보고서를 `PENDING`에서 `PROCESSING`으로 전환한 작업 하나만 본문을 생성한다.

종료된 방의 강연 시작·종료 시각 중 하나가 없거나 종료 시각이 시작 시각보다 빨라 분석 범위를 확정할 수 없으면, 서버는 보고서 LLM을 호출하지 않고 같은 `reportId`를 `PENDING`에서 `FAILED`로 전환한다. 강사에게는 공통 안내인 ‘보고서 생성에 실패했습니다.’를 표시한다. 시작과 종료가 같은 시각이면 유효한 강연으로 처리한다.

**POST** `/api/v1/rooms/{roomId}/reports` — HOST, 강연방 소유자 — Request `{}`

소유자의 수동 최초 접수 또는 기존 보고서가 `PENDING`일 때의 중복 접수 응답 — 202 Accepted

```json
{
  "data": {
    "reportId": 601,
    "roomId": 10,
    "status": "PENDING",
    "createdAt": "2026-11-17T02:00:10Z",
    "message": "회고 보고서 생성 대기 중입니다."
  }
}
```

강연자 화면에서 녹음 중에 강연 종료를 확정하면 마지막 확정 발언의 서버 저장을 확인하고 STT 세션을 종료한 뒤 강연방을 닫는다. 발언 저장에 실패하면 방을 `LIVE`로 유지하고 저장을 재시도한다. STT 종료는 이 흐름에서 처리하며 SCRUM-157은 `ENDED`인 방에 저장된 발언을 보고서 입력으로 사용한다.

보고서 본문 생성은 강연방이 `ENDED`이고 투표 응답 집계와 마지막 채팅 분석이 확정됐을 때 시작한다. 강연 `startedAt` 기준 모든 30초 AI 정규 구간과 종료 시 잔여 구간이 `COMPLETED` 또는 `FAILED`이면 채팅 분석이 확정된 것이다. 청중 채팅이 없는 구간은 LLM 호출 없이 주제 그룹 0개의 `COMPLETED` 분석으로 기록되므로 분석 누락으로 보지 않는다. 보고서 요청은 AI 분석을 새로 생성하거나 재호출하지 않는다. 종료 후 남은 채팅 구간은 청중 분석 스케줄러가 처리하고 해당 방의 최종 결과가 저장되면 보고서 작업자에게 알린다.
본문 생성은 종료된 강연의 기록이 준비된 후 비동기로 진행하고, 생성 실패 시 `FAILED`를 기록한다. 아래 HTTP 응답은 소유자의 POST 요청에 적용한다.

같은 강연방의 소유자가 생성 요청을 다시 보내면 서버는 기존 `reportId`와 현재 `status`를 반환한다. `PENDING`·`PROCESSING`이면 HTTP 202, `COMPLETED`·`FAILED`면 HTTP 200이다. 중복 요청으로 새 생성 작업을 등록하거나 LLM을 다시 호출하지 않는다.

접수 API 오류는 `401 UNAUTHENTICATED`, `403 FORBIDDEN`, `404 ROOM_NOT_FOUND`, `409 ROOM_NOT_ENDED`이다. 입력 기록의 준비 여부는 접수 후 본문 생성 단계에서 확인한다. 접수 상태는 `lecture_reports`에 저장한다.

서버가 재시작되면 DB에 접수된 `PENDING` 보고서는 같은 `reportId`로 생성 조건을 다시 확인한다. 기록이 준비됐으면 생성을 시작하고, 마지막 분석이 진행 중이면 결과가 저장될 때까지 대기한다. `PROCESSING` 보고서는 기존 작업이 중단되었고 완료 결과를 확인할 수 없을 때만 같은 보고서를 `FAILED`로 기록한다. 이 경우 LLM을 재호출하지 않으며 강사에게는 공통 생성 실패 안내를 보여준다.

### [REPORT-02, 03, 04, 05, 07] 보고서 내부 데이터 처리

별도 외부 Request API 는 없다.

SCRUM-158의 내부 진입점은 `ReportInputService.collect(roomId, hostEmail)`이다. 호출자는 인증된 강연자의 이메일을 전달한다. 서비스는 방 소유권과 종료 여부를 확인한 후 같은 DB 스냅샷에서 입력을 읽는다. 다른 방이나 강연자 채팅을 가리키는 AI 근거 연결이 발견되면 `REPORT_INPUT_NOT_READY`로 수집을 중단한다.

SCRUM-159의 `ReportInputService.collectTimeline(roomId, hostEmail)`은 같은 수집 절차로 읽은 한 강연방의 기록을 시간순으로 묶어 `timeline`과 보고서 전체의 `dataLimitations`를 반환한다. 구간을 구성할 때는 저장된 DB 기록만 사용한다.

수집 대상: `stt_segments`(실제 발언), `stt_gaps`(누락 구간), `chat_messages`(청중 채팅 원문), `ai_analyses`·`ai_topic_groups`(저장된 분석 구간과 주제별 의견 요약), `polls`·`poll_options`·`poll_responses`(일반 투표와 이해도 체크 `type=UNDERSTANDING` 의 마감된 결과).

채팅 원문은 해당 강연방에서 청중이 작성한 메시지(`participant_id IS NOT NULL`)만 수집한다. 강연자가 채팅으로만 남긴 답변은 보고서 입력에서 제외하며, 강연자의 설명은 저장된 STT 발언을 근거로 확인한다.
청중 채팅의 수집 범위는 강연방의 전체 진행 시간이다. STT 녹음 시작 전이나 중지 후에도 방이 `LIVE`인 동안 저장된 청중 메시지는 보고서 입력에 포함한다.
강연 종료 시각과 수신 시각이 같은 청중 채팅도 수집한다. 이 메시지는 마지막 60초 구간(또는 60초 미만의 마지막 구간)에 한 번만 연결한다. 강연 도중의 구간 경계에는 기존 `[start, end)` 기준을 적용한다.

보고서 LLM에 전달하는 채팅의 `participantId`에는 해당 보고서 안에서만 쓰는 `p1`, `p2` 등의 번호를 넣는다. 같은 강연방 참여자가 여러 번 작성하면 모든 메시지에 같은 번호를 사용한다. 작성자의 닉네임과 DB 참여자 ID는 작성자 정보로 전달하지 않는다. 원문 근거는 기존 `chat_messages.id`로 연결한다.

청중 채팅 원문은 `chat_messages.id`당 한 번 수집한다. 각 AI 주제 그룹에는 같은 강연방의 원문을 가리키는 관련 메시지 ID 목록을 연결한다. 어느 그룹에도 연결되지 않은 청중 채팅도 원문 목록에 포함한다. 주제별 메시지 수는 해당 그룹에 연결된 고유 메시지 ID 수로 센다.

정상 흐름: 강연 데이터 조회 → 시간순 정렬 → 60초 보고서 구간 생성 → STT 발언 연결 → 이해도 체크 결과 연결 → 청중 채팅과 저장된 30초 AI 분석 결과 연결 → 투표 결과 연결 → LLM 회고 요약 생성 → AI 결과·근거 검증 → 구조화된 보고서 JSON 저장. 보고서 생성 과정은 청중 채팅 분석 LLM을 다시 호출하지 않는다.

시간대별 연결 기준

타임라인의 첫 구간은 강연을 시작한 시각에 열린다. 예를 들어 10:00:15부터 10:02:25까지의 강연은 10:00:15~10:01:15, 10:01:15~10:02:15, 10:02:15~10:02:25로 나눈다. 기록이 없는 분도 순서대로 유지한다. 시작 시각과 종료 시각이 같으면 표시할 기록이 있을 때만 그 시각의 구간 하나를 만든다.

| 데이터 | 연결 기준 |
| --- | --- |
| STT 발언 | 저장된 발언 추정 시작·종료 시각과 겹치는 구간에 연결한다. 새 발언은 [STT 시각 산정 기준](stt.md)에 따라 서버 시계를 기준으로 추정하며, 전송이 늦어져도 처음 기록한 시간대에 표시한다. |
| STT 누락 구간 | 발언과 같은 서버 시계 기준으로 기록한 중단·복구 시각을 사용한다. 전송이 늦어져도 누락이 발생한 시간대에 연결한다. |
| 채팅 | 서버 수신 시각 |
| 이해도 체크 | 투표를 연 시각(`created_at`)이 속한 구간에 연결하고 `openedAt`·`closedAt` 을 함께 기록 |
| 일반 투표 | 투표를 연 시각(`created_at`)이 속한 구간에 한 번 표시하고 시작 시각(`openedAt`)·실제 마감 시각(`closedAt`)·최종 집계를 함께 제공 |
| AI 의견 요약 | 저장된 30초 분석 구간이 속한 분에 연결한다. 각 주제는 원문 메시지 ID를 참조한다. |

발언과 누락 구간이 분 경계를 걸치면 실제로 겹치는 각 분에서 **같은 ID와 원래 시작·종료 시각**을 보여준다. 예를 들어 위 강연에서 10:01:10~10:01:20 발언은 첫째·둘째 구간에 모두 보인다. 10:01:15에 끝나는 발언은 첫째 구간에만, 10:01:15에 시작하고 끝나는 발언은 둘째 구간에만 보인다. 강연 종료 시각에 시작하고 끝나는 기록은 마지막 구간에 한 번 포함한다.

전체 회고 요약을 생성할 때는 발언 ID마다 원문을 모델에 한 번만 전달한다. 위 예시의 발언은 하나의 `STT_SEGMENT` 근거로 전달하고, 그 근거의 `relatedWindows`에 첫째·둘째 구간을 모두 담는다.

발언의 추정 시각이 강연 시간과 전혀 겹치지 않으면 타임라인에서 제외하고, 보고서 전체의 `dataLimitations`에 ‘강연 시간에 연결할 수 없는 발언 1건이 있습니다.’처럼 발언 수를 안내한다. 원문은 강연방의 ‘저장된 발언 보기’에서 확인할 수 있다. 일부라도 겹치는 발언은 해당 구간에 원문 그대로 연결하며 이 건수에서 제외한다.

종료된 강연의 보고서를 만들 때 STT 누락 구간의 `endedAt`이 `null`이면 누락 시작부터 **강연 종료 시각**까지 겹치는 60초 구간에 안내를 표시한다. 보고서에는 원래 시작 시각과 `endedAt: null`을 유지하고, 화면에는 ‘누락 시작 10:28:20 · 복구 시각 미확인’처럼 표시한다. 같은 시간대에 저장된 청중 채팅과 투표는 각자의 연결 기준에 따라 그대로 포함한다.

이해도 체크는 강연자가 여는 `type=UNDERSTANDING` 투표이며 [투표 명세](poll.md)를 따른다. 보고서는 `CLOSED` 라운드별 `poll_responses`의 참여자별 마지막 선택만 사용하고, 이전 라운드의 선택을 다음 라운드나 체크가 없는 구간으로 이어 붙이지 않는다. 응답 변경 이력은 저장하지 않으므로 분 단위 상태 변화나 변경 횟수를 복원하지 않는다. 일반 투표와 이해도 체크는 `pollId`와 `type`으로 구분하고 같은 응답을 두 번 집계하지 않는다.

`timeline.understandingChecks`는 체크를 연 시각이 속한 60초 구간에 한 번 연결하며, `openedAt`은 투표 생성 시각, `closedAt`은 실제 마감 시각이다. 최종 결과가 시작 구간에 표시되더라도 해당 구간 종료 시점의 실시간 상태를 뜻하지 않는다. 체크가 없는 구간은 빈 배열이며 이해도 0% 또는 모두 이해함으로 해석하지 않는다.

마감 시 확정된 `totalParticipants`(누적 고유 참여자 식별자 수), `respondedParticipants`, `unrespondedParticipants`, `responseRate`와 선택별 최종 인원을 함께 기록한다. 미응답은 전체에서 응답 인원을 뺀 값이며 `NOT_UNDERSTOOD`에 합치지 않는다. 선택별 비율은 응답자 기준과 전체 참여자 기준을 구분한다. 분모가 0이면 비율은 0.0이며 응답 없음으로 표시한다. 보고서 조회 때 현재 인원으로 다시 계산하지 않는다.

이해 부족 라운드 표시를 포함할 때는 POLL-06의 기준을 따른다. `lackCount = CONFUSED + NOT_UNDERSTOOD`, `lackRatio`의 분모는 응답자 수이며 소수 첫째 자리로 반올림한다. 기본 `minCount=3`, `ratio=40` 기준을 모두 충족할 때 `lowUnderstanding=true`다. 이 수치는 해당 라운드의 관찰 결과이며 강의 전체의 이해도나 설명 실패를 뜻하지 않는다. 진행 중 라운드가 남거나 마감 집계가 확정되지 않았다면 `REPORT_INPUT_NOT_READY`로 처리한다.


하나의 60초 구간에는 같은 강연 시작 시각을 기준으로 한 30초 AI 분석 최대 두 개가 들어간다. 마지막 30초 미만의 분석은 마지막 보고서 구간에 연결한다. `audienceOpinions`는 저장된 주제마다 분석 ID·실제 분석 시작/종료 시각·원문 메시지 ID를 제공한다. 주제가 없는 `COMPLETED`는 항목을 추가하지 않는다. `FAILED`는 해당 분석 시각과 실패 상태 한 건을 남긴다. 이때도 `chatMessages`에서 원문을 읽을 수 있다.

보고서의 중심은 강연 전체 기간의 기록을 종합한 `overview`다. 60초 구간은 기록과 근거를 시간대별로 찾아보기 위한 단위이며, 각 구간마다 별도의 회고 해석을 생성하지 않는다. 이번 범위에서 `timeline.aiInterpretation`은 제외한다. `timeline`은 서버가 원문·집계·누락 구간과 저장된 청중 의견 분석 결과를 연결해 구성하고, 기존 AI 의견 요약은 원문과 구분하여 표시한다. 새 보고서 LLM은 전체 강연을 종합한 요약을 작성하며 각 요약 항목에서 관련 구간과 근거를 참조한다.

전체 강연의 첫 요약(`overview`)은 단일 문자열이 아니라 다음 세 항목의 목록으로 구성한다.

| 필드 | 표시 항목 | 의미 |
| --- | --- | --- |
| `mainInterests` | 주요 관심사 | 청중이 질문·의견·요청 등으로 관심을 표현한 주제 |
| `reviewPoints` | 보충 설명 검토 지점 | 질문과 이해도 반응을 근거로 강사가 다시 확인할 대목 |
| `suggestions` | 다음 강연을 위한 제안 | 근거를 바탕으로 제시하는 검토용 개선안 |

각 목록 항목에는 `text`, 관련 시간대 목록인 `relatedWindows`, 근거 기록 목록인 `evidence`를 포함한다. 시간대는 보고서의 60초 구간을 참조하며, 여러 시간대에 걸친 내용은 여러 구간을 연결할 수 있다. 근거는 기록 종류(`type`)와 해당 기록 ID(`id`)를 함께 참조해 서로 다른 테이블의 같은 숫자 ID를 구분한다.

`evidence.type`은 아래 세 종류만 허용한다. 일반 요약 항목과 `perspectives`에 동일하게 적용한다.

| type | id가 참조하는 기록 | 근거 상세 |
| --- | --- | --- |
| `CHAT_MESSAGE` | `chat_messages.id` | 청중 채팅 원문 |
| `STT_SEGMENT` | `stt_segments.id` | 강사 확정 전사 원문 |
| `POLL_RESULT` | `polls.id` | 최종 응답자가 1명 이상인 마감 투표의 질문·선택지·최종 집계 |

일반 투표와 이해도 체크 모두 `POLL_RESULT`로 참조하고 해당 투표의 `type`(`GENERAL` 또는 `UNDERSTANDING`)으로 구분한다. 별도의 집계 ID나 개인 응답 ID를 근거 ID로 사용하지 않는다. 투표 근거 상세에는 응답·미응답 인원과 선택별 집계를 보여주며 청중 개인별 선택은 노출하지 않는다. 서버는 각 참조가 같은 강연방의 실제 보고서 입력에 존재하는지 검증하고, `POLL_RESULT`는 마감과 최종 집계 확정 여부도 검증한다. 허용하지 않은 유형이나 유효하지 않은 참조는 기존 형식·근거 검증 실패 정책을 따른다.

최종 응답자가 0명인 일반 투표와 이해도 체크는 타임라인에 ‘응답 0명’으로 표시하고, AI에 전달하는 인용 가능 근거 목록에서 제외한다. 같은 방에 청중 채팅이나 다른 투표 응답이 있어 요약을 생성하더라도 이 기준을 적용한다. 요약 항목이나 상반 의견의 개별 입장이 0명 투표를 인용하면 기존 근거 검증 실패(`INVALID_REPORT_EVIDENCE`)로 처리한다.

주요 관심사, 보충 설명 검토 지점, 다음 강연 제안의 각 항목은 해당 내용을 뒷받침하는 청중 채팅(`CHAT_MESSAGE`) 또는 응답자가 1명 이상인 마감 투표(`POLL_RESULT`)를 최소 1건 인용한다. 강사 발언(`STT_SEGMENT`)은 설명의 맥락을 보충하는 근거로 함께 인용할 수 있다. 상반된 의견은 각 입장(`perspectives`의 각 원소)에 이 기준을 적용한 뒤 상위 항목의 근거를 합친다. 일반 항목이나 개별 입장에 청중 근거가 없으면 `INVALID_REPORT_EVIDENCE`로 처리한다.

요약 항목 및 각 `perspectives`의 근거로 허용하는 대상은 청중 채팅 원문, STT 발언 원문, 서버가 마감된 투표의 최종 응답으로 계산한 이해도 체크 집계와 일반 투표 결과다. 이해도 집계와 투표 결과는 집계 범위와 원본 기록으로 추적 가능해야 하며 LLM이 수치를 생성하지 않는다. 기존 AI 의견 요약(`ai_analyses`·`ai_topic_groups`)은 주제 파악을 위한 참고 자료로만 사용하고 `evidence`의 직접 근거로 허용하지 않는다. 기존 AI 요약의 내용을 채택하려면 해당 내용을 뒷받침하는 허용된 원문 또는 집계를 직접 연결하고 검증한다. 원문·집계가 뒷받침하지 못하면 해당 내용을 요약에 포함하지 않는다. 누락 구간과 분석 실패 상태는 데이터 한계를 설명하는 자료로 유지하며 청중 의견이나 이해 상태의 증거로 해석하지 않는다.

근거는 같은 강연방의 실제 입력 기록에 존재해야 하며 해당 항목의 내용을 뒷받침해야 한다. 관련 시간대만 연결하고 근거 기록을 생략하지 않는다. `mainInterests`, `reviewPoints`, `suggestions`는 각각 최대 3개 항목을 포함한다. 충분한 근거가 있는 항목만 포함하며, 개수를 채우려고 내용을 생성하지 않는다. 근거가 있는 항목이 없으면 해당 목록은 빈 배열로 둔다. 첫 요약에 선택되지 않은 기록도 시간대별 상세 내용에서 확인할 수 있다. 보충 설명 검토 지점은 설명 실패의 확정 판정이 아니며, 다음 강연을 위한 제안은 AI가 작성한 검토용 제안으로 구분한다.

첫 요약에 포함하기 위한 최소 질문·의견 수를 일괄적으로 제한하지 않는다. 한 건의 기록도 해당 내용을 뒷받침하면 사용할 수 있지만, 한 건을 반복된 의견이나 다수 청중의 요구로 확대하지 않는다. 반복 여부·메시지 수·참여자 수는 실제 기록으로 확인되는 범위에서만 표현하고 서로 구분한다. 개선 제안은 해당 근거를 참고한 검토용 제안으로 표현하며 설명 실패의 확정 판정으로 쓰지 않는다.

같은 주제에 대한 상반된 청중 의견은 첫 요약에서 하나의 항목으로 묶되, 각 입장의 내용과 이를 뒷받침하는 근거 기록을 구분해 함께 보여준다. 서로 다른 입장의 근거를 단일 의견의 근거처럼 합치거나 한쪽 의견을 삭제하지 않는다. 관련 시간대도 각 입장과 연결해 확인할 수 있게 한다. 이러한 항목은 해당 목록의 최대 3개 제한에서 1개로 센다. 개선 제안은 의견 차이를 고려한 검토용 제안으로 작성하고, 근거 없이 한쪽 입장이 전체 청중을 대표한다고 단정하지 않는다.

청중 채팅이 없어도 일반 투표 하나에서 서로 반대되는 선택지에 각각 1명 이상 응답했다면 두 입장을 한 카드로 보여줄 수 있다. 예를 들어 ‘더 빠르게’ 6명, ‘더 천천히’ 4명이면 각 입장이 같은 `POLL_RESULT`를 인용하고 카드 전체의 근거에는 해당 투표를 한 번만 담는다. 이 투표에서 ‘더 빠르게’ 10명, ‘더 천천히’ 0명이면 응답자가 선택한 ‘더 빠르게’만 요약한다.

각 입장이 일반 투표를 인용할 때는 투표 근거(`POLL_RESULT`의 `id`)에 그 입장을 뒷받침하는 모든 선택지 ID를 `optionIds` 목록으로 연결한다. 서버는 각 선택지가 인용한 투표에 속하고 최종 응답이 1건 이상인지 확인한다. 입장의 근거를 열면 마감된 투표의 전체 결과를 보여주고, 연결된 각 선택지의 원래 문구와 최종 응답 수를 함께 강조한다. 예를 들어 ‘조금 더 빠르게’ 4명, ‘훨씬 더 빠르게’ 2명, ‘더 천천히’ 3명인 투표에서 ‘속도를 높여 달라’는 입장의 근거를 열면 세 선택지가 모두 보이고 앞의 두 선택지와 각각의 응답 수가 강조된다.

상반된 의견이 있는 항목에만 `perspectives` 목록을 채운다. 각 입장은 `text`, `evidence`, `relatedWindows`를 가지며, 각 입장별로 근거와 관련 시간대 검증을 수행한다. 일반 항목의 `perspectives`는 빈 배열이다. 상반 의견의 LLM 초안은 상위 `evidence`와 `relatedWindows`를 빈 배열로 두고 2개 이상의 입장을 제공한다. 일반 항목은 기존의 상위 `text`, `evidence`, `relatedWindows`를 사용한다. 상반 의견 항목의 상위 `text`는 의견 차이를 요약하고, 상위 `evidence`와 `relatedWindows`는 검증된 입장별 목록을 서버에서 합쳐 구성한다. LLM에 상위 근거·시간대를 중복 생성하도록 요구하지 않는다. 근거는 `(type, id)`, 시간대는 `(startAt, endAt)` 기준으로 중복을 제거하되 서로 다른 60초 구간을 하나의 연속 구간으로 병합하지 않는다. 상위 합집합은 탐색용이며 각 입장과 근거의 연결은 `perspectives` 안에 유지한다. 어느 한 입장의 검증에 실패해도 해당 입장을 조용히 버리지 않고 기존 정책대로 보고서 생성을 실패 처리한다.

첫 요약 후보가 많으면 다음 기준으로 각 목록의 최대 3개 항목을 선택한다.

| 항목 | 우선 선택 기준 |
| --- | --- |
| 주요 관심사 | 서로 다른 참여자가 언급한 주제를 우선하고, 여러 시간대에 반복해서 나타났는지도 참고한다. |
| 보충 설명 검토 지점 | 구체적인 질문·요청과 관련 이해도 체크의 최종 '헷갈림'·'모르겠음' 응답을 함께 검토한다. 체크의 시작·마감 범위를 확인하며 60초 구간 연결만으로 특정 발언에 대한 응답이라고 단정하지 않는다. |
| 다음 강연을 위한 제안 | 근거가 명확하고 강사가 실행할 수 있는 구체적인 제안을 우선한다. |

한 이해도 체크에서 응답만 갈린 경우, 첫 요약에 선정하면 `reviewPoints` 한 항목에 체크의 시작·마감 시각과 최종 응답 분포를 표시한다. 예를 들어 ‘이해됨’ 6명, ‘헷갈림’ 4명은 한 체크의 집계로 보여주며 `perspectives`는 빈 배열로 둔다. 재설명을 요청한 관련 채팅이 있으면 같은 항목에 해당 `CHAT_MESSAGE`를 연결해 원문을 열어볼 수 있게 한다. 재설명 요청은 그 채팅을 인용하고, ‘헷갈림’을 선택한 응답자 전체의 요청으로 확대하지 않는다.

체크 마감 후에 올라온 재설명 요청도 같은 강연의 기록에서 해당 체크와 같은 주제를 가리키는 게 분명하면 그 항목의 근거로 연결한다. 채팅 원문은 실제 작성 시각의 타임라인 구간에 한 번만 두고, 요약 항목에서 그 기록을 참조한다. 예를 들어 10시 15분에 마감된 가스비 계산 체크에 10시 17분의 “아까 가스비 계산 예시를 다시 보여주세요”를 연결해도 채팅의 표시 시각은 10시 17분이다. 어느 주제를 가리키는지 모호한 요청은 원래 시간대의 채팅 기록에만 남긴다.

위 기준은 우선순위이며 필수 포함 조건이나 인과관계 판정 기준이 아니다. 한 참여자의 질문도 근거가 있으면 포함할 수 있다. 메시지 반복 횟수를 서로 다른 참여자 수로 취급하지 않고, 참여자 수는 저장된 강연방 참여자 식별자를 기준으로 집계한다. 이 값이 실제 서로 다른 사람 수를 보장하는 것으로 표현하지 않는다.

청중의 채팅·마감된 이해도 체크 응답·일반 투표 응답이 없고 STT 발언 기록만 있는 경우에는 보고서 LLM을 호출하지 않는다. 기존 생성 조건이 충족되면 서버가 발언 기록과 누락 구간을 시간대별로 구성하고, `overview`의 세 목록을 모두 빈 배열로 둔 보고서를 `COMPLETED`로 저장한다. `dataLimitations`에는 '청중 반응 기록이 부족해 관심사와 보충 설명 지점을 판단하기 어렵습니다.'를 포함한다. 청중의 관심사·이해 상태·보충 설명 필요성을 추측하지 않으며, 반응 부재를 모두 이해했다거나 관심이 없었다는 뜻으로 해석하지 않는다. 강연자가 생성한 투표가 있더라도 응답이 없으면 청중 반응이 있는 것으로 보지 않는다. 분석 실패 등 별도의 데이터 한계가 있으면 관련 안내도 유지한다.

청중 기록은 있지만 해당 시간대의 STT가 누락된 경우에도 청중 기록으로 확인되는 관심사와 그 기록에 근거한 검토용 제안은 포함할 수 있다. 누락된 강사의 설명 내용을 만들어 내거나, 설명이 부족했다거나 답변하지 않았다고 단정하지 않는다. 해당 구간과 관련 회고 항목에서 발언 기록이 없어 설명·답변 여부를 확인하기 어렵다는 한계를 표시하고, `dataLimitations`에도 포함한다. 관측된 청중 기록과 누락된 발언에 대한 판단 불가능 상태를 구분한다.

보고서 LLM 호출 또는 출력의 형식·근거 검증에 실패하면 자동 재시도나 재생성 없이 보고서 상태를 `FAILED`로 기록한다. 존재하지 않는 기록 ID 또는 다른 강연방의 기록 참조는 근거 검증 실패로 처리한다. 사용자에게는 보고서 생성 실패 안내를 표시하며, 실패한 AI 결과나 내부 오류 상세를 완료 결과처럼 노출하지 않는다. 원본 발언·청중 기록은 변경하거나 삭제하지 않는다. 보고서 조회나 중복 생성 요청을 자동 재호출의 경로로 사용하지 않으며, 저장된 청중 채팅 분석도 다시 호출하지 않는다. 보고서 LLM의 입력·출력 토큰 상한 결정은 보류한다.

일부 청중 의견 분석(`ai_analyses`)이 `FAILED`여도 다른 생성 조건이 충족되면 보고서를 생성한다. 성공한 분석 결과는 재사용하고, 실패한 분석 구간의 채팅 원문·STT·이해도·투표 등 남아 있는 기록은 전체 강연 요약의 근거로 활용할 수 있다. 이때 실패한 청중 의견 분석을 재호출하거나, 보고서 요약을 해당 분석의 성공 결과처럼 취급하지 않는다.

분석 실패 구간은 시간대별 상세에서 '청중 의견 AI 분석 실패'로 표시하고, `dataLimitations`에도 관련 시간대와 함께 안내한다. 빈 채팅 구간의 정상 `COMPLETED`(주제 그룹 0개), 아직 완료되지 않은 분석, `FAILED` 분석을 구분한다. 모든 분석 구간의 상태가 확정되어야 한다는 기존 생성 조건은 유지한다. 보고서 LLM 호출 또는 결과 검증 자체가 실패한 경우에는 별도로 보고서 상태를 `FAILED`로 처리한다.

강연 전체에 STT 발언·청중 채팅·이해도 응답·투표 응답이 전혀 없으면 보고서 LLM을 호출하지 않는다. 기존 생성 조건이 충족된 경우 서버가 `overview`의 세 목록을 모두 빈 배열로 구성하고, `dataLimitations`에 '수집된 기록이 없어 요약할 수 없습니다.'를 포함한 보고서를 `COMPLETED`로 저장한다. 이는 시스템 오류로 인한 `FAILED`와 구분한다. STT 누락 구간이나 청중 의견 분석 실패 기록이 있으면 시간대별 상세와 관련 안내를 유지하며, 응답 없는 투표 생성 기록만으로 요약할 청중 반응이 있다고 판단하지 않는다.

데이터 한계는 보고서 전체의 `dataLimitations`와 영향받는 각 요약 항목 및 `perspectives` 입장의 `limitations`에 표시한다. 두 필드는 서버가 실제 입력 기록·STT 누락 구간·청중 분석 실패 상태를 기준으로 구성하는 안내 문자열 배열이며, LLM에 생성이나 판정을 맡기지 않는다. 항목·입장에 적용되는 한계가 없으면 `limitations`는 빈 배열이다. 서버는 검증된 관련 시간대와 근거 기록의 범위를 실제 누락·실패 구간과 대조해 영향을 연결한다. 각 입장의 한계는 해당 입장에 유지하고 상위 항목에도 중복을 제거해 반영한다. 보고서 전체의 한계를 무관한 모든 항목에 일괄 복사하지 않는다. 구간에 관한 안내에는 해당 시간대를 포함하며, 원문이 남아 있는 분석 실패와 STT 기록 누락을 서로 다른 한계로 표현한다. 최종 저장·조회 JSON에 서버가 구성한 한계를 포함하고 조회 시 LLM을 호출하지 않는다.

**GET** `/api/v1/rooms/{roomId}/reports` — HOST, 강연방 소유자

보고서 LLM 호출과 출력 검증에서 발생한 실패는 다음 세 코드로 구분해 기록한다. 사용자에게는 강연 시간 오류로 생성 전에 실패한 경우까지 포함해 위의 공통 안내를 표시한다. 내부 실패 코드는 응답에 포함하지 않는다.

| 내부 실패 코드 | 의미 |
| --- | --- |
| `LLM_REQUEST_FAILED` | LLM API 오류·시간 초과·잔액 부족 등 호출 실패 |
| `INVALID_REPORT_FORMAT` | JSON 파싱 또는 보고서 스키마 검증 실패 |
| `INVALID_REPORT_EVIDENCE` | 존재하지 않는 기록·다른 강연방 기록·마감되지 않은 투표 등 허용되지 않는 근거 참조 |

실패한 LLM 결과나 공급자 오류 원문은 사용자에게 노출하지 않는다. 세 경우 모두 자동 재시도·재생성을 하지 않으며, 조회 및 중복 생성 요청도 저장된 실패 상태를 반환한다. 내부 기록에는 API 키 등 시크릿을 남기지 않는다.

규칙: 보고서가 없으면 404, 접수 후 대기 중이면 PENDING, 생성 중이면 PROCESSING, 실패면 FAILED, 완료는 저장된 JSON 반환. 조회는 새 보고서 접수나 LLM 호출을 유발하지 않는다. 다른 강연방 보고서 조회는 차단한다.


### 전체 강연 요약 생성 (SCRUM-156·160)

LLM 출력 계약은 [초안 스키마](../../backend/src/main/resources/report/report-draft.schema.json), 검증 후 서버 조립 계약은 [완성 스키마](../../backend/src/main/resources/report/report-content.schema.json), 생성 지침은 [시스템 프롬프트](../../backend/src/main/resources/report/report-system-prompt.txt)에 둔다. LLM은 `overview`만 생성하고 서버 전용 필드는 반환하지 않는다. 시간대별 원문은 서버가 조립한다.

Spring의 `ReportOverviewService.generate(roomId, hostEmail)`은 인증된 소유자의 종료 강연 데이터를 한 번 수집한다. 이 스냅샷에서 인용 가능한 원문·집계와 각각의 시간대를 구성하고, 청중 근거가 있으면 OpenAI Responses API를 한 번 호출한다. 키는 `OPENAI_API_KEY`, 모델은 `OPENAI_REPORT_MODEL`로 설정하며 기본 모델은 `gpt-6-luna`다. 청중 근거가 없으면 빈 요약을 서버에서 구성한다.

서비스는 검증된 요약과 서버가 조립한 타임라인·데이터 한계를 `ReportContent`로 반환하거나 세 가지 내부 실패 사유를 호출자에게 전달한다. SCRUM-157의 작업자는 생성 상태와 검증된 결과를 `lecture_reports`에 함께 저장한다. 저장된 상태와 결과를 읽는 공개 조회 API는 SCRUM-161의 범위다. 서버는 참조의 종류·ID·선택지·시간대를 대조한다. 채팅과 체크의 주제 일치 여부 등 문맥에 대한 판단은 프롬프트와 요약 품질 평가에서 다룬다.

실험 시 사용한 입력과 생성 결과는 [실험 실행 방법](../../scripts/report_experiment/README.md)과 [기존 4개 샘플 결과](../experiments/report-results.json)에서 확인할 수 있다.
