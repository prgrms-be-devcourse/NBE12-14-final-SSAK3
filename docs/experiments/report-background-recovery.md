# 강연 회고 보고서 생성 장애 복구

팀 공유용 구현 보고서 · 2026-11-26

## 강사가 경험하는 변화

밤 9시에 강연을 끝내고 서버가 멈췄다고 가정하자. OpenAI가 밤 10시에 보고서를 완성했고 우리 DB에 응답 ID가 있다면, 다음 날 오전 6시에 다시 켜진 서버는 그 ID로 결과를 가져온다. 강사가 다시 요청할 필요가 없고, 새 보고서 생성 비용도 들지 않는다.

응답 ID를 저장하기 전에 연결이 끊어지면 상황이 다르다. 강연 종료 화면과 내 강연 기록에 **결과 확인 중**이 뜬다. 서버는 이 상태를 감지하는 즉시 생성 자리를 비운다. 강사는 원본 결과를 기다리거나 **보고서 생성 다시 시도**를 바로 한 번 누를 수 있다. 재시도를 여러 탭에서 동시에 눌러도 한 번만 접수한다.

| 상황 | 서버 동작 | 강사에게 보이는 결과 |
| --- | --- | --- |
| 강연은 종료됐고 아직 생성 시도를 시작하지 않았다 | DB에 남은 접수 건을 찾아 입력이 준비되고 자리가 생기면 처리한다 | 생성 대기 |
| OpenAI에 접수했고 응답 ID를 저장했다 | 같은 ID를 주기적으로 조회한다. 완료 알림으로도 처리를 시작할 수 있다 | 생성 중 → 회고 보고서 보기 |
| 요청을 보냈을 수 있으나 응답 ID가 없다 | 미확정으로 기록하고 자리를 반납한다. 뒤늦은 알림은 요청할 때 보낸 시도 식별자로 연결한다 | 결과 확인 중. 남은 재시도 1회를 즉시 사용 가능 |
| 재시도를 눌렀는데 작업자가 생성 자리를 확보하기 전에 원본 보고서가 저장됐다 | 같은 보고서가 이미 완료된 것을 확인하고 대기 중인 재시도를 끝낸다 | 완성된 보고서 한 건 |
| 원본과 재시도가 모두 발송됐다 | 같은 보고서에서 **검증을 통과해 먼저 DB에 저장된 결과**를 채택한다. 늦은 응답은 별도로 정리한다 | 먼저 완성된 보고서가 그대로 유지됨 |
| 재시도도 미확정이다 | 자리를 다시 반납한다. 이후 들어오는 두 시도의 유효한 결과를 복구할 수 있다 | 결과 확인 중. 추가 생성 버튼은 사라짐 |
| 재시도는 확실히 실패했으나 원본 결과를 아직 복구할 수 있다 | 원본은 계속 확인한다. 원본이 성공하면 보고서를 열고, 원본까지 실패하거나 복구 기한이 지나면 재시도의 실패 사유를 표시한다 | 결과 확인 중. 추가 생성 기회는 이미 사용함 |
| ID를 끝내 찾지 못하고 미확정 상태로 30일이 지났다 | 해당 시도의 입력 복사본을 지우고 복구를 종료한다. 이후 확인한 해당 응답은 삭제 대상으로 등록한다 | 확인 기간 종료. 재시도를 사용하지 않았다면 한 번 요청 가능 |
| 보고서를 DB에 저장한 직후 외부 삭제가 실패했다 | 삭제할 ID가 DB에 남아 다음 작업에서 다시 삭제한다 | 저장 직후부터 보고서를 읽을 수 있음 |

## 두 자리와 재시도 한 번의 의미

백그라운드 모드에서는 같은 MySQL을 쓰는 서버들이 **생성 자리 두 개를 공유**한다. OpenAI가 대기 중이거나 생성 중이라고 확인한 정상 요청은 끝날 때까지 한 자리를 쓴다. 두 자리가 차면 다음 보고서는 DB에 대기한다. 메모리 작업 대기열이 가득 차거나 서버를 재시작해도 접수한 보고서는 다음 복구 주기에 다시 확인한다.

즉시 재시도는 **강사가 지금 접수할 수 있다**는 뜻이다. 두 자리에 다른 정상 보고서가 있다면 재시도도 자리가 날 때까지 대기한다. 미확정 건 때문에 별도의 3분 타이머를 두지는 않는다. 전송 중 서버가 멈춘 경우에는 재시작 직후 또는 다른 서버의 복구 주기에 작업 연결이 끊긴 것을 감지해 자리를 반납한다.

원본이 이미 외부에 접수됐을 가능성은 남는다. 미확정 원본이 외부에서 계속 실행되는 동안 새 요청을 보내면 일시적으로 OpenAI에서 실행되는 실제 작업 수가 두 개를 넘거나, 같은 강연에 생성 비용이 두 번 들 수 있다. 화면에서 재시도 전에 이 가능성을 안내한다.

## 결과를 복구하고 삭제하는 순서

1. 외부에 보내기 전에 강연방, 시도 식별자, 해당 시점의 보고서 입력, 생성 자리를 MySQL에 함께 기록한다. 청중 자료가 없는 강연은 로컬 기록만으로 보고서를 완성한다.
2. OpenAI Responses API에 백그라운드 생성과 응답 저장을 요청한다. 서버가 만든 시도 식별자를 메타데이터로 보내고 반환된 응답 ID를 DB에 연결한다. 전송 여부가 불확실하면 서버가 같은 생성을 자동으로 다시 보내지 않는다.
3. 서명된 완료 알림은 수신 목록에 먼저 저장한다. 작업자가 해당 응답을 조회해 우리 시도와 일치하는지 확인한다. 응답 ID를 이미 알면 웹훅 없이도 조회할 수 있다. 재전달된 알림이나 같은 OpenAI 프로젝트의 다른 서비스 알림이 다른 강연의 보고서를 바꾸지 않는다.
4. 생성 시점에 저장한 입력을 기준으로 AI 초안의 형식과 인용 근거를 검증한다. 검증한 본문 저장과 외부 응답 삭제 예약을 같은 DB 트랜잭션으로 처리한다. DB 저장이 실패하면 트랜잭션이 취소되므로 같은 결과를 다시 가져와 저장할 수 있다.
5. 별도 작업자가 저장된 응답을 OpenAI에서 삭제한다. 삭제가 실패하면 재시도하고, 앞선 삭제가 성공해 이미 사라진 경우에도 완료로 처리한다. 강사가 보고서를 열 때는 서비스 DB의 본문을 읽는다. [OpenAI 응답 삭제 API](https://developers.openai.com/api/reference/resources/responses/methods/delete)

**보관 기간.** 우리 서비스는 ID를 잃은 시도의 입력 복사본을 30일간 복구에 사용하며 기한이 지나면 정리한다. OpenAI는 일반 프로젝트에서 명시적으로 저장한 Responses 응답의 기본 보관 기간을 30일로 안내하며, 프로젝트의 데이터 정책에 따라 동작이 달라진다. 우리 서비스는 DB에 보고서를 저장하는 즉시 **OpenAI 쪽 응답**을 삭제 대상으로 등록한다. 웹훅 전송에 실패하면 OpenAI는 최대 72시간 동안 간격을 늘려 재시도한다. 이 기간 안에서도 전달 횟수와 시각은 유동적이다. [OpenAI 데이터 보관 정책](https://developers.openai.com/api/docs/guides/your-data) · [OpenAI 웹훅 전달 정책](https://developers.openai.com/api/docs/guides/webhooks)

## 배포 담당자에게 전달할 내용

- 기본값은 `OPENAI_REPORT_BACKGROUND_ENABLED=false`다. 외부 응답 저장을 사용하려면 프로젝트의 데이터 보관 설정과 보고서 모델의 백그라운드 지원을 확인한다. 같은 MySQL을 사용하는 모든 서버에 V15와 새 코드를 먼저 반영한다. [OpenAI 백그라운드 모드](https://developers.openai.com/api/docs/guides/background)
- OpenAI 프로젝트에서 `POST /api/v1/webhooks/openai`의 공개 HTTPS 주소를 등록한다. `response.completed`, `response.failed`, `response.incomplete`, `response.cancelled`를 선택하고 서명 키를 `OPENAI_REPORT_WEBHOOK_SECRET`으로 설정한다. 각 서버에 같은 설정을 반영한 후 백그라운드 모드를 켠다. [배포 절차](../aws/deployment.md)
- Discord 수신 주소는 기존 `REPORT_ALERT_WEBHOOK_URL`이다. OpenAI 웹훅은 서비스가 결과를 **받는** 용도이고, Discord 웹훅은 개발자에게 장애 알림을 **보내는** 용도다. 전송 결과가 불분명하면 개발자에게는 보고서 번호와 `REPORT_DISPATCH_UNKNOWN (요청 전달 여부 미확정)`이 전달된다. 강사는 강연 종료 화면과 내 강연 기록에서 상태를 확인한다.
- 기능을 다시 끌 때는 기존 백그라운드 시도의 조회·수동 재시도·삭제가 끝날 때까지 같은 프로젝트의 API 키와 웹훅 설정을 유지한다. 구버전 서버로 되돌리면 새 시도의 복구 작업을 수행할 수 없다. [상태 API](../api/report.md) · [기존 설계 결정](../adr/0002-report-recovery.md)

### 실제 OpenAI로 백엔드 재시작 검증

2026-11-26에 합성 채팅 한 건을 넣은 강연으로 실제 생성을 한 번 실행했다. 테스트 전용 MySQL과 두 개의 백엔드 JVM을 사용했다. 로컬 테스트 릴레이는 두 번째 생성 POST를 차단하고, 두 JVM이 같은 OpenAI 응답에 접근했는지 관찰했다.

| 시점 | 확인한 결과 |
| --- | --- |
| 첫 JVM 실행 | OpenAI가 `queued`를 반환했다. MySQL에 응답 ID와 `PROCESSING` 상태가 커밋됐고 보고서 본문은 비어 있었다. |
| 첫 JVM 강제 종료 후 | 두 번째 JVM을 시작하기 전에 같은 응답 ID를 OpenAI에 조회해 `completed`를 확인했다. 이 시점에도 서비스 DB 본문은 비어 있었다. |
| 새 JVM 실행 | 백엔드가 완료된 원본을 한 번 조회해 검증한 뒤 같은 보고서에 저장했다. DB는 `COMPLETED`, 생성 시도 한 건, 최초와 같은 응답 ID, `retry_used=false`였다. 외부 응답 삭제도 확인했다. |

실제 생성 POST는 **1회**였고 OpenAI 응답의 사용량은 **입력 2,415토큰, 출력 38토큰, 합계 2,453토큰**이었다. 이 한 번의 실호출은 임시 로컬 실행기로 수행했다.

### PR에서 실행하는 모의 재시작 테스트

`develop` 또는 `main` 대상 PR의 백엔드 CI는 로컬 모의 OpenAI 서버로 다음 두 경우를 검증한다. 두 테스트 모두 실제 백엔드 프로세스를 강제 종료하고 같은 MySQL에 연결한 새 프로세스를 시작한다. OpenAI 토큰 사용량은 0개다.

| 백엔드 종료 시점 | 재시작 후 확인할 동작 |
| --- | --- |
| 응답 ID를 DB에 저장한 직후 | 저장된 ID로 기존 결과를 가져와 보고서를 완성한다. 모의 서버가 받은 생성 요청은 처음 한 건뿐이다. |
| 백엔드가 모의 OpenAI의 응답 ID를 확인하고 DB에 쓰기 직전 | 복구 후 생성 자리가 비고, 로그인한 강사가 완료 알림 없이 같은 보고서를 즉시 다시 요청한다. 재시도 API를 연달아 두 번 호출해도 모의 서버가 받은 생성 요청은 최초 한 건과 재시도 한 건이다. DB에는 재시도로 만든 본문이 저장된다. |

로컬에서 두 경우를 재현하려면 테스트 전용 `react_test` DB를 준비한 뒤, Git Bash에서 다음 명령을 실행한다. 테스트는 해당 전용 DB를 초기화하고 테스트가 띄운 백엔드 프로세스만 종료한다.

```bash
cd backend
RUN_REPORT_RESTART_TEST=true ./gradlew test --rerun --tests '*BackgroundReportWorkflowIntegrationTest.recoversAfterBackend*'
```
