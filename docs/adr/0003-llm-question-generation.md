# LLM 문제 생성의 실행 방식

문제는 `concepts`를 근거로 Anthropic Claude API가 만든다. 호출은 대결 중이 아니라 관리자가 `POST /admin/questions/generate`로 시작한 생성 작업에서만 일어난다. 서버를 띄우는 것만으로는 호출이 일어나지 않아야 비용과 "대결 중 LLM 호출 금지" 규칙을 함께 지킬 수 있다. 앱 시작 플래그로 한 번 돌리는 방식도 검토했으나 관리자가 화면에서 실행할 수 있어야 해서 관리자 API를 택했고, 이 API는 `docs/api-spec.md`에 추가한다.

생성은 서버 백그라운드에서 실시간 호출로 진행하고 요청은 바로 202를 돌려준다. 진행 상태는 서버 메모리에만 두고 DB 작업 테이블은 만들지 않는다. 문제 하나를 만들 때마다 따로 커밋하므로 서버가 꺼져도 저장된 문제는 남고 만들던 문제 하나만 잃는다. 서버 종료 시에는 만들던 문제까지만 마무리하고(최대 55초 대기, `docker-compose.yml`의 `stop_grace_period: 60s`) 멈추며, 끊긴 작업을 자동으로 재개하지 않는다. 강제 종료(`kill -9`, 전원, 인스턴스 장애)는 막을 수 없고 그때는 만들던 문제 하나와 그 호출 비용만 잃는다. 다시 실행하면 연결된 문제가 가장 적은 개념부터 채우므로 같은 개념에 몰리지 않는다.

Message Batches API(50% 할인, 결과는 최대 24시간 안에 수거)는 쓰지 않는다. 서버가 꺼지면 Anthropic 쪽 배치는 계속 진행되고 과금되는데 배치 ID를 잃어 결과를 찾지 못하며, 이를 막으려면 작업 테이블과 마이그레이션이 필요하다. 생성과 검증(SCRUM-94)이 두 단계라 대기도 두 번이다. 문제 100개 기준 절감액이 몇 달러 수준이라 MVP 범위에서는 얻는 것보다 복잡도가 크다. 호출부는 인터페이스(`QuestionGenerator`) 뒤에 두어 비용이 문제가 되면 Batch 구현으로 바꿀 수 있게 한다.

기본 모델은 `claude-sonnet-5-5`이며 `LLM_MODEL` 환경 변수로 바꾼다. 생성 요청의 `model`로 모델을 고를 수 있지만 자유 입력은 받지 않고, 허용 목록(`LLM_MODELS`, 기본 haiku·sonnet·opus 5.5)과 기본 모델만 호출 전에 통과시킨다. 오타로 호출이 전부 실패하거나 실수로 단가가 높은 모델을 고르는 일을 막기 위해서다. 어떤 모델로 만들었는지는 문제에 저장하지 않는다(스키마와 ERD를 바꾸지 않기 위함). 서버 로그와 상태 조회에만 남으므로 모델별 품질을 사후에 비교해야 하면 `questions`에 컬럼을 추가하는 별도 작업이 필요하다. 오답 후보 풀은 쓰지 않고 문제마다 보기 4개와 해설을 한 번에 만든다. 풀을 쓰면 어떤 조합에서도 정답이 하나인지 검증(SCRUM-94)해야 해서 범위가 커지기 때문이다. 정답 위치가 한쪽으로 몰리지 않도록 보기 순서는 서버가 섞는다.

난이도 기준(쉬움·보통·어려움이 무엇을 요구하는가)은 점수 표와 별개로 `docs/game-rules.md`의 "난이도 기준"에 정의한다. 프롬프트, 검증, 관리자 검수가 같은 기준을 쓴다.

첫 실제 호출(3문제)에서 두 가지 문제가 확인되어 서버 검증을 더했다. 세 문제 모두 정답이 가장 긴 보기여서 프롬프트에 길이 규칙을 넣고 정답이 오답 평균의 1.3배를 넘으면 다시 만든다. 어려움으로 요청한 문제가 정의·분류를 고르는 수준이어서, 모델이 문제를 쓰기 전에 풀이 단계(`solvingSteps`)를 먼저 적게 하고 어려움은 2단계 미만이면 다시 만든다. 풀이 단계는 모델의 자기 신고라 난이도를 보장하지 않는다. 최종 판단은 SCRUM-94의 별도 검증 호출과 사람 검수가 맡는다.
