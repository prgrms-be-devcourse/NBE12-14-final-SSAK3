# RE:ACT — 기능 정의서

구현 범위와 비즈니스 규칙의 기준 문서다. REST·STOMP 형식은 `docs/api-spec.md`, DB는 `docs/db/erd.dbml`과 Flyway 마이그레이션을 따른다.
원문의 "정상 흐름 / 데이터 변화 / Security" 항목은 아래 규칙에 녹여 압축했다. P0 는 MVP 필수, P1 은 완성도 향상, P2 는 추후 확장이다.

## 0. 서비스 목적과 설계 원칙

강연자의 실제 발언과 청중의 채팅·이해도 반응·투표 결과를 수집하고, 시간대별로 연결해 강연 중 소통과 종료 후 회고를 지원한다.

핵심 사용자 흐름: 강연방 생성 → QR 로 청중 입장 → 강연 시작 및 STT 기록 → 실시간 채팅·이해도·투표 수집 → AI 의견 분석 → 강연 종료 → 시간대별 데이터 연결 → AI 회고 보고서 생성

- 실시간 채팅과 LLM 분석은 독립적으로 처리한다.
- 음성 인식은 브라우저에서 수행하고, 확정된 전사 결과만 서버에 저장한다.
- 발언·채팅·이해도·투표는 강연방 ID 와 발생 시각을 기준으로 연결한다.
- 같은 시간대에 발생한 반응을 특정 발언의 직접적인 결과라고 단정하지 않는다.
- AI 분석 결과에는 실제 원본 데이터와의 연결 정보를 남기고, AI 생성 요약·제안과 실제 수집 데이터를 구분한다.
- AI 실패 시에도 채팅·이해도·투표는 유지한다.
- 종료된 강연방은 새 채팅·이해도·투표 응답을 받지 않는다.
- P0 는 발언과 반응을 일정 시간 구간으로 묶으며, 문장 단위 정밀 원인 분석은 하지 않는다.

모든 권한 검증은 서버에서 하고(REST 와 WebSocket 모두), 클라이언트가 보낸 userId·participantId·역할 문자열을 신뢰하지 않는다.

## 2. ROOM — 강연방 관리 (P0)

| ID | 기능 | 규칙 |
| --- | --- | --- |
| ROOM-01 | 강연방 생성·참여 코드 발급 | 입력은 제목(필수)·설명(선택), 생성자가 강연자가 됨(클라이언트가 지정 불가), 참여 코드는 서버가 생성하며 유일·추측 어려움, 생성 직후 상태 READY |
| ROOM-02 | QR·참여 링크 | 소유자만 발급, 기존 joinCode 재사용, QR 이미지는 영구 저장하지 않고 요청 시 생성, 링크에 관리자 인증 정보 포함 금지, 링크를 안다고 강연자 권한이 생기지 않음 |
| ROOM-03 | 강연방 조회 | 강연자용 관리 정보와 청중 공개 정보를 구분(제목·설명·상태·시작 시각), 청중은 소유자 정보 등 비공개 정보 조회 불가 |
| ROOM-04 | 강연 시작·종료 | 소유자만 가능, READY → LIVE → ENDED, READY 에서만 시작·LIVE 에서만 종료, ENDED 재시작 없음, 시작·종료 시각을 서버에 기록, 종료 시 진행 중 투표 종료·잔여 STT/채팅/분석 상태 확인, 데이터가 확정되기 전에는 보고서를 완료로 표시하지 않음, STT 녹음은 브라우저 마이크 권한 확인 후 별도 시작 |
| ROOM-05 | 청중 비회원 입장 | 입력은 joinCode·닉네임, 유효 코드·비종료 강연만, 참여자 ID 는 서버 생성, 같은 닉네임이어도 서로 구분, 참여자 식별 정보 위조 방지, 이해도·투표 중복 집계 방지에 식별자 사용 |
| ROOM-06 | 권한 구분·접근 제어 | 생성·시작·종료는 소유자만, 청중은 자신이 참여한 강연의 허용 기능만, 닉네임·역할 문자열을 권한 기준으로 쓰지 않음, 다른 강연방의 채팅·이해도·투표·STT·보고서 접근 차단 |
| ROOM-07 | 종료 후 참여·응답 제한 | ENDED 에서 신규 입장·채팅·투표 응답(이해도 체크 포함) 차단, 종료 직전 STT 최종 저장은 정책에 따라 허용, 기존 기록 조회는 허용, 프론트 버튼 비활성화에 의존하지 않고 서버가 상태를 확인 |

## 3. CHAT — 실시간 채팅 (P0)

| ID | 기능 | 규칙 |
| --- | --- | --- |
| CHAT-01 | 강연방별 WebSocket 채팅 | LIVE 상태의 해당 강연방 참가자만, 강연방별 독립 채널, 채팅은 AI 분석 완료를 기다리지 않고 AI 장애와 무관 |
| CHAT-02 | 메시지 DB 저장 | 강연방 ID 와 함께 저장, 시각은 서버 기준 `receivedAt`, AI 전처리에서 제외된 채팅도 원문은 남김, 저장이 확인된 메시지를 AI 분석 대상으로 삼음, 저장 실패 시 전송 성공 여부·재시도 정책을 명확히 정의 |
| CHAT-03 | 채팅 내역 조회 | 해당 강연방 메시지만, 서버 수신 시각 순, 페이지·커서 기반, 종료된 강연도 권한이 있으면 조회 가능, 결과는 messageId·작성자 표시 정보·content·receivedAt |
| CHAT-04 | 유효성 검증 | null·공백·최대 길이 초과 거부, XSS 대응, 일반 질문·의견을 임의로 제거하지 않음, AI 전처리 제외와 채팅 전송 거부는 별개 정책 |
| CHAT-05 | 강연방 간 격리 | 모든 메시지는 하나의 강연방에 속함, 다른 강연방 메시지의 구독·조회·전송 차단, DB 조회와 WebSocket 구독 양쪽에 적용, 메시지의 강연방 ID 위조 방지 |

작성자는 청중 또는 강연자이며(`chat_messages` 의 `participant_id`/`host_user_id` 중 정확히 하나), 강연자도 채팅할 수 있다. AI 청중 의견 분석은 청중 메시지만 대상으로 한다.

## 4. POLL — 실시간 투표와 이해도 체크 (P0)

투표 종류(`type`)는 두 가지다. `GENERAL` 은 강연자가 질문과 선택지를 직접 쓰는 일반 투표이고, `UNDERSTANDING` 은 이해도 체크로 선택지가 `UNDERSTOOD`(이해됨)·`CONFUSED`(헷갈림)·`NOT_UNDERSTOOD`(모르겠음)로 고정된다.
이해도 체크는 별도 기능이 아니라 투표의 한 종류이며, 청중이 상시로 누르는 상태 버튼은 없다. 강연자가 체크를 열면 투표 한 번(라운드)이 시작되고 마감되면 끝난다. 미응답은 별도로 취급하며 모르겠음으로 간주하지 않는다.

| ID | 기능 | 규칙 |
| --- | --- | --- |
| POLL-01 | 투표 생성·마감 | 소유자만, LIVE 에서만 생성, `GENERAL` 은 질문과 선택지 검증(P0 는 단일 선택), `UNDERSTANDING` 은 선택지를 서버가 고정(클라이언트가 보낸 선택지는 무시), 제한 시간(초)은 강연자가 투표마다 선택하며 기본 60초이고 허용 범위는 서버가 검증, 서버가 마감 시각(`closesAt`)을 계산해 저장, 강연방당 진행 중(OPEN) 투표는 1개만 허용하고 이미 있으면 거절, 강연자는 마감 전에 조기 마감 가능, `closesAt` 에 도달하면 자동 마감, 강연 종료 시 진행 중 투표도 마감, 생성 시 청중에게 알림 |
| POLL-02 | 청중 응답 | LIVE 이고 투표가 OPEN 이며 `closesAt` 이전일 때만, 해당 강연방 참가자만, 마감 전까지 자기 선택을 바꿀 수 있고 같은 선택을 반복해도 달라지지 않음, 선택지는 해당 투표에 속해야 함, 다른 참가자의 응답 수정 금지, 마감 여부는 서버 시각으로 판단하고 마감 후 요청은 거절, 마감 시점의 마지막 선택이 자동으로 최종 응답이 되며(별도 제출 없음) 선택하지 않고 마감되면 미응답 |
| POLL-03 | 최종 응답·중복 방지·집계 | `(pollId, participantId)` 당 응답은 1건이고 변경하면 덮어씀(중간 변경 이력은 남기지 않고 마지막 변경 시각만 보관), 중복 저장 방지(서버에서 검증), 동시 변경에도 최종 선택과 집계가 일치, 선택지별 응답 수 합계는 전체 응답 수와 일치, 마감·강연 종료 후 결과는 변하지 않음, 중복 요청으로 총 응답 수가 늘지 않음, 결과는 투표를 연 강연방의 소유자(강연자)만 진행 중에도 실시간으로 조회하고 청중에게는 공개하지 않음 |
| POLL-05 | 이해도 체크 집계 | `UNDERSTANDING` 투표에만 적용, 응답 인원은 최종(현재) 선택이 있는 고유 청중 수, 미응답 = 전체 − 응답, 전체 참여 인원은 누적 고유 참가자 기준이고 현재 접속 인원과 구분, 상태 비율의 분모는 전체 참여 인원이며 응답자 대비 비율은 별도로 표시하고 구분, 청중 개개인의 선택을 공개하지 않음 |

POLL-04(다양한 투표 유형)는 P2 에 있다. 이해도 체크도 투표 종류의 하나이므로, 새 유형을 늘릴 때는 같은 `type` 으로 구분한다.
구 FEED-ID 대응: FEED-01~06 → POLL-05(공통 규칙은 POLL-01~03), FEED-07·08 → POLL-06, FEED-09 → POLL-07, FEED-10 → 삭제.

## 5. STT — 강연자 발언 기록 (P0)

| ID | 기능 | 규칙 |
| --- | --- | --- |
| STT-01 | 음성 인식 시작·중지 | 소유자만, LIVE 에서만, 마이크 권한과 브라우저 지원 필요, 임시 인식 결과와 확정 결과를 구분해 확정 결과만 서버에 저장, 강연 종료 시 STT 도 종료, STT 실패가 채팅·이해도·투표를 중단시키지 않음, 청중의 마이크를 쓰지 않음 |
| STT-02 | 발언 텍스트·시각 저장 | 발언은 강연방·STT 세션에 연결, 서버 수신 시각과 발언 추정 시각을 구분(브라우저가 정확한 시각을 주지 않으면 추정값임을 명시), 같은 구간의 중복 저장을 막기 위해 segmentId(segmentKey) 사용, 저장 실패 시 재전송·누락 상태 처리 |
| STT-03 | 강연방 연결·격리 | STT 세션은 하나의 강연방에 속함, 소유자 요청만, 세션 ID 위조·다른 강연 접근 차단, 보고서에는 해당 강연의 STT 만 사용 |
| STT-04 | 오류·중단 감지·누락 구간 | 중단되면 정상 기록 중인 것처럼 표시하지 않음, 중단·재시작 시각과 사유를 누락 구간으로 기록, 기록 없는 구간의 발언을 AI 가 지어내지 않음, 보고서에서 데이터 누락으로 표시, 자동 재시작이 실패해도 수동 재시작 경로 제공, 오류 응답에 민감 정보 금지 |
| STT-05 | 발언 기록 조회 | 소유자만, 시간순, segmentId·transcript·시각·상태 반환, 누락 구간은 발언으로 채우지 않음, 다른 강연 기록 접근 금지 |

## 6. AI-CHAT — 청중 의견 분석 (P0)

| ID | 기능 | 규칙 |
| --- | --- | --- |
| AI-CHAT-01 | 주기적 채팅 수집 | LIVE 중 강연 `startedAt` 기준 분석 주기(기본 30초) 정규 구간을 만들고, 구간은 `[start, end)` 로 처리한다. 강연방별 청중 채팅을 서버 수신 시각 `receivedAt` 기준으로 조회하며, 채팅 수신과 AI 분석은 비동기다. 스케줄러 지연·재시작 뒤에는 `startedAt`부터 현재 시각까지 완전히 종료된 정규 구간 중 `ai_analyses` 기록이 없는 구간을 시간순으로 처리하며, 이미 기록된 구간은 상태와 관계없이 재호출하지 않는다. 청중 채팅이 없는 구간도 `ai_analyses` 에 기록하되 LLM 은 호출하지 않고 `COMPLETED`(`model_name`은 null, 주제 그룹 0개)로 완료한다. 종료 후에는 `endedAt`까지 남은 30초 미만 잔여 구간을 별도 분석 대상으로 확정해 비동기로 처리한다. 강연 종료 API는 이 분석 완료를 기다리지 않는다. 분석 스케줄러가 해당 방의 마지막 결과를 확정하면 보고서 작업자에게 알린다. P0 는 MySQL 배치 조회로 시작(Redis Streams 큐는 P2), 서버 내부 작업 |
| AI-CHAT-02 | LLM 채팅 분석 | Gemini API의 `GEMINI_MODEL` 설정값(로컬 예시 `gemini-3.5-flash-lite`)을 사용, 실제 채팅에 근거한 내용만, 질문뿐 아니라 이해 부족 표현·의견도 분석, 구조화된 JSON 출력을 요청·서버에서 재검증, AI 작성 내용을 사용자 원문처럼 표시하지 않음, API 키는 서버 보관, 개인정보 최소화, 프롬프트 인젝션 대응 |

## 12. 기능 간 연계 규칙

- **강연방과 청중**: 강연방은 한 명의 생성 강연자를 가지고, 청중은 강연방별 참여자 식별자를 가진다. 채팅·이해도·투표·STT·AI 분석·보고서는 모두 강연방을 기준으로 관리하며, 참여 링크와 관리 권한은 분리한다.
- **STT 와 시간**: 발언 텍스트와 발생 시각을 저장하고 시간 정밀도는 실제 테스트로 확인한다. 채팅 수신과 이해도 체크의 시작·마감·최종 응답은 서버 시각을 쓰고, 보고서는 공통 시간 기준·고정 구간 단위로 연결한다.
- **이해도와 투표**: 이해도 체크는 투표의 한 종류이며 라운드마다 청중당 최종 응답 하나를 저장한다. 실시간 분포는 진행 중인 투표의 현재 선택, 보고서의 시간대별 변화는 마감된 라운드 결과로 계산한다. 미응답과 모르겠음은 다르다.
- **AI 분석**: 채팅은 실시간, 분석은 비동기로 처리하고 결과는 근거 메시지와 연결한다. 정규 분석 구간은 `startedAt` 기준 30초 `[start, end)` 이며, 빈 구간도 LLM 호출 없이 `COMPLETED`로 기록한다. 종료 후 잔여 구간까지 확정되면 해당 방의 대기 중인 보고서가 생성 조건을 확인한다.
- **회고 보고서**: 종료된 강연만 대상으로 하고 STT·채팅 질문·이해도 체크 결과·투표를 활용한다. 보고서는 같은 `startedAt` 기준 60초 `[start, end)` 구간을 사용하며, 해당 범위의 저장된 30초 AI 분석 결과를 재사용하고 LLM을 다시 호출하지 않는다. 모든 정규 분석 구간과 종료 잔여 구간이 `COMPLETED` 또는 `FAILED`로 확정되기 전에는 생성하지 않는다. 시간대 연결은 관찰이지 인과가 아니며 AI 생성 요약과 실제 기록을 구분한다. 누락 구간은 표시만 하고 보완하지 않는다.

## 13. MVP 성공 기준 (Definition of Done)

**강연방·인증**
- [ ] 강연자가 회원가입·로그인·로그아웃할 수 있다.
- [ ] 강연방 생성과 고유 참여 코드 발급이 가능하다.
- [ ] QR 코드·참여 링크로 청중이 입장할 수 있다.
- [ ] 강연자·청중 권한이 구분된다.
- [ ] 강연 시작·종료 상태가 정상 변경되고, 종료된 강연의 신규 응답이 차단된다.

**채팅**
- [ ] 강연방별 실시간 채팅이 가능하고 DB 에 저장되며 내역을 조회할 수 있다.
- [ ] 빈 메시지·길이 초과 메시지를 차단한다.
- [ ] 서로 다른 강연방의 메시지가 섞이지 않는다.

**이해도·투표**
- [ ] 청중이 세 상태 중 하나를 선택할 수 있고 참여자별 최신 상태가 하나만 유지된다.
- [ ] 상태 변경 이력이 시간과 함께 저장된다.
- [ ] 강연자가 이해도 체크를 열고 청중이 제한 시간 안에 응답하며, 이해도 인원·비율·미응답 인원을 확인할 수 있다.
- [ ] 강연자가 투표를 생성·마감하고 청중이 마감 전까지 응답·수정할 수 있으며, 중복 투표와 집계 오류를 방지한다.

**STT**
- [ ] 강연자가 음성 인식을 시작·중지할 수 있고 전사 텍스트와 시각이 강연방과 연결되어 저장된다.
- [ ] 음성 인식 오류·중단과 누락 구간을 확인할 수 있다.
- [ ] 강연자가 시간대별 발언 기록을 조회할 수 있다.

**AI 채팅 분석**
- [ ] 강연방별 채팅을 주기적으로 분석하고 유사 주제별로 청중 의견(질문·의견·요청·이해 부족 표현)을 그룹화·요약하고 유형을 분류한다.
- [ ] 결과를 DB 에 저장·조회하고 원본 메시지와 연결한다.
- [ ] AI API 실패 시 채팅·이해도·투표가 유지된다.

**대시보드**
- [ ] 실시간 채팅, 이해도 인원·비율, 투표 결과, AI 주제별 의견, 관련 원문을 확인할 수 있다.

**회고 보고서**
- [ ] 강연 종료 후 보고서를 생성하고 저장·재조회할 수 있다.
- [ ] STT·채팅·이해도·투표 데이터를 수집해 반복 주제를 요약하고 시간대별 발언과 청중 반응을 연결한다.
- [ ] AI 회고 요약 초안을 생성하고, AI 생성 내용과 실제 근거 데이터를 구분한다.
- [ ] STT 누락 구간과 확인되지 않은 내용을 사실로 단정하지 않는다.

**테스트·배포**
- [ ] 공개 URL로 이용할 수 있고 HTTPS/WSS 가 동작한다.
- [ ] 주요 API 단위·통합 테스트, 강연방 간 격리, 이해도·투표 정합성, 시간대 연결을 검증한다.
- [ ] 10~20명 모의 강연과 강연 생성부터 보고서 조회까지의 전체 흐름을 검증한다.
