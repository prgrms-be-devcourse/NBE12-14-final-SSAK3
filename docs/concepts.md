# 개념 초안 (concepts 시드용)

SCRUM-92. `concepts` 테이블에 넣을 개념 50개(분야당 10개)의 초안이다.

- 각 항목의 이름은 `concepts.name`, 본문은 `concepts.description`이 된다. 분야는 `categories` 순서(1~5)를 따른다.
- 설명은 AI 가 쓴 **초안**이다. LLM 문제 생성의 근거가 되므로 팀이 공식 문서·교재로 확인한 항목만 시드에 반영한다.
- 항목마다 `검수` 체크박스에 확인한 사람을 적는다. 틀리거나 모호한 문장은 바로 고친다.
- 개념 이름이 같은 항목이 둘 이상 생기지 않게 한다(`name` UNIQUE).
- 참고한 주제 목록: kjsu0209/Tech-Interview (MIT). 문장은 옮기지 않고 새로 썼다.

## 검수 때 특히 볼 것

- 숫자·기본값: HTTP 상태 코드, 포트, 시간 복잡도, 헤더 크기(UDP 8바이트).
- MySQL 동작: TRUNCATE 가 롤백되지 않는 점, InnoDB 기본 격리 수준(REPEATABLE READ)과 팬텀 리드.
- 같은 이름의 개념을 다르게 설명한 곳이 없는지(예: REST 와 GET/POST 의 멱등성 설명).

## 1. 네트워크 (category_id = 1)

### 1-1. TCP 3-way handshake
- 검수: [ ] (    )

TCP 연결을 맺기 위한 3단계 절차다. 클라이언트가 SYN을 보내고, 서버가 SYN+ACK로 응답하며, 클라이언트가 ACK를 보내면 연결이 수립된다. 이 과정에서 양쪽이 초기 시퀀스 번호를 교환해 동기화하고, 서로 송수신이 가능한지 확인한다. 연결 종료는 FIN과 ACK를 주고받는 4-way handshake로 이루어진다. SYN Flooding은 공격자가 다수의 SYN 요청을 보내 서버가 SYN-RECEIVED 상태의 연결 요청을 처리하도록 만들고, 마지막 ACK를 보내지 않아 연결 대기 자원을 소모시키는 공격이다. 운영체제와 네트워크 장비는 SYN 쿠키 등으로 이를 완화할 수 있다.

### 1-2. TCP와 UDP의 차이
- 검수: [ ] (    )

TCP는 연결 지향 프로토콜로, 시퀀스 번호와 확인 응답, 재전송 등을 통해 신뢰성과 데이터 순서를 보장하고 흐름 제어·혼잡 제어를 수행한다. UDP는 연결 설정 절차가 없고 전달·순서·재전송을 보장하지 않으며 헤더가 8바이트로 작다. UDP가 항상 TCP보다 빠른 것은 아니며, 애플리케이션이 필요한 신뢰성이나 혼잡 제어를 직접 구현할 수도 있다. TCP는 웹·파일 전송 등에, UDP는 실시간 통신·게임·DNS 질의 등에 활용된다.

### 1-3. HTTP 상태 코드
- 검수: [ ] (    )

1xx는 정보, 2xx는 성공(200 OK, 201 Created, 204 No Content), 3xx는 리다이렉션(301 영구 이동, 302 임시 이동), 4xx는 클라이언트 오류(400 잘못된 요청, 401 인증 필요, 403 권한 없음, 404 찾을 수 없음), 5xx는 서버 오류(500 내부 오류, 502 Bad Gateway, 503 서비스 불가)를 뜻한다. 401은 인증 정보가 없거나 유효하지 않은 상태로 응답에 `WWW-Authenticate` 헤더를 함께 보내며, 올바른 인증 정보로 다시 요청하면 해결될 수 있다. 403은 서버가 요청을 이해했지만 현재 인증된 사용자에게 해당 요청을 수행할 권한이 없어 거부한 상태로, 같은 인증 정보로 다시 요청해도 결과가 같다. 자원의 존재를 숨기려고 403 대신 404를 쓰기도 한다.

### 1-4. HTTPS와 TLS
- 검수: [ ] (    )

HTTPS는 HTTP에 TLS(과거 SSL)를 얹어 통신을 암호화한 프로토콜이다. 기밀성(암호화), 무결성(변조 방지), 서버 인증(인증서)을 제공한다. 핸드셰이크에서 서버 인증서를 검증하고 키 교환 과정을 통해 공유 비밀을 생성한 뒤, 이를 바탕으로 세션 키를 파생한다. 이후 데이터는 효율적인 대칭키 암호화로 보호한다. 기본 포트는 443이다.

### 1-5. DNS
- 검수: [ ] (    )

도메인 이름을 IP 주소로 변환하는 분산 계층 시스템이다. 클라이언트의 질의를 받은 리졸버가 루트 → TLD → 권한(Authoritative) 네임서버 순으로 물어 답을 찾고, 결과는 TTL 동안 캐시한다. 대표 레코드는 A(IPv4), AAAA(IPv6), CNAME(별칭)이다.

### 1-6. CORS
- 검수: [ ] (    )

브라우저는 동일 출처 정책에 따라 다른 출처(프로토콜·호스트·포트가 다른 경우)의 리소스에 대한 스크립트의 접근을 제한한다. 서버가 `Access-Control-Allow-Origin` 등의 응답 헤더로 허용하면 브라우저가 응답 접근을 허용한다. GET·HEAD·POST이면서 안전한 헤더만 쓰는 단순 요청은 사전 요청 없이 바로 보내지만, 이때도 응답에 허용 헤더가 없으면 브라우저가 스크립트에 응답을 넘기지 않는다. 그 밖의 요청은 본 요청 전에 `OPTIONS` 메서드로 사전 요청(preflight)을 보낸다. 쿠키 같은 인증 정보를 포함한 요청에서는 응답에 `Access-Control-Allow-Credentials: true`가 있어야 하고, `Access-Control-Allow-Origin`에는 `*` 대신 특정 출처를 지정해야 한다. 사전 요청 응답에도 이 헤더가 필요하다. CORS는 브라우저의 보안 정책이므로 일반적인 서버 간 통신에는 적용되지 않는다.

### 1-7. OSI 7계층
- 검수: [ ] (    )

네트워크 통신을 7개 계층으로 나눈 참조 모델이다. 1계층 물리(비트 전송, 케이블·허브·리피터), 2계층 데이터 링크(MAC 주소 기반 프레임 전달, 스위치·브리지), 3계층 네트워크(IP 주소 기반 경로 결정, 패킷 단위, 라우터), 4계층 전송(종단 간 통신, TCP 세그먼트·UDP 데이터그램, TCP/UDP), 5계층 세션(통신 세션의 수립·유지·종료), 6계층 표현(데이터 형식 변환·암호화·압축), 7계층 응용(응용 프로그램에 네트워크 서비스 제공, HTTP·FTP·SMTP)이다. 계층을 나누면 문제가 생긴 계층만 고칠 수 있다. 실제 인터넷은 4계층인 TCP/IP 모델을 따른다.

### 1-8. 로드 밸런싱
- 검수: [ ] (    )

여러 서버에 요청을 나눠 한 서버에 부하가 몰리지 않게 하고 가용성을 높이는 기술이다. 분산 방식에는 순서대로 나누는 라운드 로빈, 서버 성능에 가중치를 주는 가중치 라운드 로빈, 연결이 가장 적은 서버로 보내는 최소 연결, 클라이언트 IP로 서버를 고정하는 IP 해시가 있다. 헬스 체크로 장애가 난 서버를 분산 대상에서 뺀다. L4 로드 밸런서는 IP·포트를, L7 로드 밸런서는 URL·헤더 같은 HTTP 내용을 기준으로 분산한다. 세션을 서버 메모리에 두면 같은 서버로 계속 보내야 하므로 고정 세션이나 세션 외부 저장소가 필요하다.

### 1-9. GET과 POST의 차이
- 검수: [ ] (    )

GET은 리소스 조회에 주로 사용한다. 일반적으로 파라미터를 URL 쿼리 문자열에 담으며, HTTP 의미상 안전하고 멱등한 메서드다. 캐시와 북마크에 활용할 수 있고, 요청 URL 길이는 브라우저·서버 등 구현 환경에 따라 제한될 수 있다. POST는 리소스 생성이나 처리를 요청할 때 주로 사용하고 데이터를 요청 본문(body)에 담는다. 일반적으로 멱등하지 않아 같은 요청을 반복하면 여러 번 처리될 수 있으며 기본적으로 캐시되지 않는다. 요청 본문도 HTTPS를 사용하지 않으면 암호화되지 않으므로 POST 자체가 보안을 보장하지는 않는다.

### 1-10. 웹소켓
- 검수: [ ] (    )

하나의 TCP 연결에서 클라이언트와 서버가 양방향으로 실시간 데이터를 주고받는 프로토콜이다. HTTP/1.1에서는 Upgrade 헤더를 이용한 핸드셰이크(응답 코드 101 Switching Protocols)를 거쳐 연결을 유지하며, 서버가 먼저 메시지를 보낼 수 있다. HTTP/2에서는 Upgrade와 101을 쓰지 않고 확장된 CONNECT 메서드(RFC 8441)로 시작한다. 폴링처럼 요청마다 HTTP 헤더를 반복해 보내지 않아 오버헤드가 작다. 채팅, 게임, 실시간 알림에 쓰고 주소는 `ws://`, TLS를 쓰면 `wss://`이다.

## 2. 운영체제 (category_id = 2)

### 2-1. 프로세스와 스레드
- 검수: [ ] (    )

프로세스는 실행 중인 프로그램으로, 코드·데이터·힙·스택으로 이루어진 독립된 메모리 공간을 가진다. 스레드는 프로세스 안의 실행 단위로, 코드·데이터·힙은 공유하고 스택과 레지스터는 스레드마다 따로 가진다. 프로세스 사이에서 통신하려면 IPC가 필요하지만, 스레드는 공유 메모리를 쓰므로 통신이 빠르다. 대신 공유 자원을 동시에 수정하면 Race Condition이 생겨 동기화가 필요하다. 한 스레드에서 치명적 오류가 나면 같은 프로세스의 다른 스레드도 영향을 받는다.

### 2-2. 데드락
- 검수: [ ] (    )

둘 이상의 프로세스가 서로 상대가 가진 자원을 기다리며 영원히 진행하지 못하는 상태다. 상호 배제, 점유 대기, 비선점, 순환 대기 네 조건이 모두 성립할 때 발생한다. 해결 방법은 조건 하나를 없애는 예방, 안전한 상태만 허용하는 회피(은행원 알고리즘), 발생 후 찾아서 복구하는 탐지·회복으로 나눈다.

### 2-3. 뮤텍스와 세마포어
- 검수: [ ] (    )

뮤텍스는 임계 구역에 한 번에 하나의 스레드만 들어가게 하는 상호 배제 락이다. 일반적인 뮤텍스 구현에서는 락을 획득한 스레드가 해제해야 하며, 세부 소유권 규칙은 운영체제나 라이브러리의 구현에 따라 정의된다. 세마포어는 정수 카운터로 동시에 접근할 수 있는 수를 N개까지 허용하며, `wait(P)`와 `signal(V)` 연산으로 조작한다. 값이 0과 1뿐인 이진 세마포어는 뮤텍스와 비슷하지만 소유권이 없어 다른 스레드가 해제할 수 있고, 실행 순서를 맞추는 동기화에도 쓴다.

### 2-4. 가상 메모리
- 검수: [ ] (    )

가상 메모리는 프로세스마다 독립적인 가상 주소 공간을 제공하고, 실제 물리 메모리보다 큰 주소 공간을 사용할 수 있게 하는 메모리 관리 기법이다. MMU와 페이지 테이블을 이용해 가상 주소를 물리 주소로 변환하며, 요구 페이징을 통해 필요한 페이지만 메모리에 적재할 수 있다. 메모리에 없는 페이지에 접근하면 페이지 폴트가 발생한다. 운영체제는 접근이 유효한지 확인한 뒤 필요한 경우 파일이나 스왑 영역에서 페이지를 읽거나 새 페이지를 할당한다. 페이지 폴트가 지나치게 자주 발생해 실제 작업보다 페이지 교체에 많은 시간이 쓰이는 상태를 스래싱이라고 한다.

### 2-5. 페이지 교체 알고리즘
- 검수: [ ] (    )

빈 프레임이 없을 때 메모리의 어떤 페이지를 내보낼지 정하는 방법이다. FIFO는 가장 먼저 들어온 페이지를 교체하며 프레임 수를 늘려도 페이지 폴트가 늘 수 있는 Belady의 모순이 생길 수 있다. LRU는 가장 오래 사용되지 않은 페이지를 교체한다. 최적(Optimal) 알고리즘은 앞으로 가장 오래 사용되지 않을 페이지를 교체해 폴트가 가장 적지만 미래를 알아야 하므로 구현할 수 없고, 다른 알고리즘의 성능을 비교하는 기준으로 쓴다.

### 2-6. 컨텍스트 스위칭
- 검수: [ ] (    )

CPU가 실행하던 프로세스(또는 스레드)에서 다른 것으로 전환할 때, 현재 상태(레지스터, 프로그램 카운터 등)를 PCB(스레드는 TCB 등 운영체제가 쓰는 태스크 관리 구조)에 저장하고 다음 대상의 상태를 복원하는 과정이다. 전환하는 동안에는 유용한 작업을 하지 못하므로 순수한 오버헤드다. 전환 과정에서 캐시와 TLB의 적중률이 낮아져 성능이 일시적으로 떨어질 수 있지만, 이들이 매번 완전히 비워지거나 무효화되는 것은 아니다. 같은 프로세스의 스레드끼리 전환할 때는 주소 공간을 바꾸지 않아 보통 프로세스 간 전환보다 가볍다.

### 2-7. CPU 스케줄링
- 검수: [ ] (    )

준비 큐의 프로세스 중 다음에 CPU를 쓸 것을 고르는 정책이다. 선점형은 실행 중인 프로세스에서 CPU를 빼앗을 수 있고(Round Robin, SRTF), 비선점형은 프로세스가 스스로 반납할 때까지 기다린다(FCFS, SJF). SJF는 실행 시간이 가장 짧은 작업을 선택하는 비선점형 알고리즘이고, SRTF는 남은 실행 시간이 가장 짧은 작업을 선택하는 선점형 알고리즘이다. FCFS는 단순하지만 긴 작업 뒤에서 짧은 작업이 오래 기다리는 호위 효과(convoy effect)가 있다. SJF는 작업의 실행 시간을 알 수 있고 모두 동시에 도착한다고 가정하면 평균 대기 시간이 가장 짧지만, 긴 작업이 계속 밀리는 기아가 생길 수 있다. Round Robin은 타임 퀀텀 단위로 순환해 응답성이 좋지만 퀀텀이 너무 작으면 컨텍스트 스위칭 오버헤드가 커진다.

### 2-8. Race Condition
- 검수: [ ] (    )

둘 이상의 스레드나 프로세스가 공유 자원에 동시에 접근하고, 실행 순서에 따라 결과가 달라지는 상태다. 예를 들어 두 스레드가 같은 변수에 `count++`를 하면 읽기-증가-쓰기가 원자적이지 않아 증가분이 사라질 수 있다. 공유 자원에 접근하는 임계 구역에 한 번에 하나만 들어가게(상호 배제) 하면 막을 수 있다. 방법은 뮤텍스 같은 락, 세마포어, 모니터(`synchronized`), 원자 연산(CAS)이다. 임계 구역 문제의 해결 조건은 상호 배제, 진행, 한정 대기다.

### 2-9. 커널 모드와 유저 모드
- 검수: [ ] (    )

CPU 실행 권한을 나눈 두 가지 모드다. 커널 모드는 하드웨어와 메모리 전체에 접근할 수 있고 운영체제 핵심 코드가 실행된다. 유저 모드는 제한된 권한으로 일반 애플리케이션이 실행된다. 유저 프로그램이 파일·네트워크·프로세스 생성처럼 특권이 필요한 일을 하려면 시스템 콜을 호출해 커널 모드로 전환했다가 결과를 받고 유저 모드로 돌아온다. 시스템 콜은 시스템 콜 전용 명령이나 트랩 같은 메커니즘으로 커널 모드에 제어를 넘기며, 모드 전환에는 비용이 든다.

### 2-10. 동기와 비동기, 블로킹과 논블로킹
- 검수: [ ] (    )

블로킹과 논블로킹은 작업을 요청한 호출자(스레드)가 결과를 기다리는 동안 대기 상태에 머무는지에 관한 구분이다. 블로킹 호출은 작업이 완료될 때까지 호출한 스레드가 대기하고, 논블로킹 호출은 작업이 완료되지 않았더라도 제어를 즉시 반환한다. 동기와 비동기는 작업의 완료 및 결과 처리를 호출자가 직접 확인·수행하는지, 작업이 완료되면 콜백·이벤트 등으로 통지받아 처리하는지에 관한 구분이다. 동기 논블로킹 방식에서는 호출자가 즉시 반환된 뒤 결과를 반복 확인(폴링)할 수 있다. 비동기 방식은 완료 통지를 받아 후속 처리를 수행한다. 동기/비동기와 블로킹/논블로킹은 서로 독립된 기준이라, 비동기라고 해서 항상 논블로킹인 것은 아니다.

## 3. 데이터베이스 (category_id = 3)

### 3-1. 트랜잭션과 ACID
- 검수: [ ] (    )

트랜잭션은 하나의 논리적 작업 단위로, 모두 반영(commit)되거나 모두 취소(rollback)된다. ACID는 네 가지 성질이다. 원자성은 전부 수행되거나 전혀 수행되지 않는 것, 일관성은 수행 전후에 제약 조건을 만족하는 것, 격리성은 동시에 실행되는 트랜잭션이 서로 간섭하지 않는 것, 지속성은 커밋된 결과가 장애가 나도 유지되는 것이다. 격리성의 강도는 격리 수준(READ COMMITTED, REPEATABLE READ 등)으로 조절한다.

### 3-2. 인덱스
- 검수: [ ] (    )

검색 속도를 높이기 위해 컬럼 값과 행의 위치를 정렬해 따로 저장하는 자료구조다. 일반적으로 B-tree 계열(B+Tree)을 쓰며 동등 비교와 범위 검색, 정렬에 유리하고, 복합 인덱스는 선두 컬럼부터 조건에 쓰여야 활용된다. 해시 인덱스는 동등 비교에만 쓸 수 있고 범위 검색과 정렬 최적화에는 쓸 수 없다. 일반적인 MySQL InnoDB 인덱스는 B-tree 계열(BTREE)이며 `USING`으로 지정할 수 있는 타입도 BTREE뿐이다. 이와 별도로 InnoDB는 텍스트 검색용 FULLTEXT 인덱스와 공간 데이터용 SPATIAL 인덱스(R-tree)를 지원한다. 해시 인덱스는 MEMORY 엔진의 기본 인덱스이고, InnoDB는 자주 조회되는 값에 대해 내부적으로 어댑티브 해시 인덱스를 자동으로 만들 수 있다. 인덱스는 INSERT·UPDATE·DELETE 때 함께 갱신해야 해서 쓰기가 느려지고 저장 공간을 더 쓴다. 조건절·조인·정렬에 자주 쓰이는 컬럼을 후보로 검토하며, 카디널리티가 높은 컬럼은 효율이 좋은 경우가 많지만 실제 효과는 조회 조건·데이터 분포·선택도·쓰기 빈도에 따라 달라진다.

### 3-3. 정규화
- 검수: [ ] (    )

데이터 중복을 줄여 삽입·수정·삭제 이상을 막기 위해 테이블을 분리하는 과정이다. 제1정규형은 모든 컬럼이 원자값을 갖는 것, 제2정규형은 제1정규형을 만족하면서 후보키의 일부에만 종속되는 부분 함수 종속을 제거한 것이다. 제3정규형은 제2정규형을 만족하면서 비주요 속성이 후보키에 이행적으로 종속되는 문제를 제거한 것이다. 지나치게 정규화하면 조인이 늘어 조회가 느려질 수 있어, 성능을 위해 일부러 중복을 허용하는 역정규화를 하기도 한다.

### 3-4. 트랜잭션 격리 수준
- 검수: [ ] (    )

동시에 실행되는 트랜잭션이 서로의 변경을 얼마나 볼 수 있는지 정한 단계다. 낮은 수준부터 READ UNCOMMITTED, READ COMMITTED, REPEATABLE READ, SERIALIZABLE이다. 이상 현상은 커밋되지 않은 값을 읽는 Dirty Read, 같은 행을 다시 읽었더니 값이 달라지는 Non-repeatable Read, 같은 조건으로 다시 조회했더니 행이 늘거나 줄어드는 Phantom Read가 있다. SQL 표준에서 각 수준이 허용하는 이상 현상은 READ UNCOMMITTED가 세 가지 모두, READ COMMITTED가 Non-repeatable Read와 Phantom Read, REPEATABLE READ가 Phantom Read, SERIALIZABLE이 없음이다. 표준은 반드시 허용해야 하는 현상이 아니라 허용될 수 있는 현상의 상한을 정하므로, DBMS 구현은 표준보다 엄격할 수 있다. 일반적으로 격리 수준이 높을수록 동시성이 낮아지거나 잠금 대기가 늘어날 수 있다. MySQL InnoDB의 기본 격리 수준은 REPEATABLE READ이다. InnoDB는 일반적인 일관 읽기에서 트랜잭션 스냅샷을 사용하며, 잠금 읽기에서는 넥스트 키 락 등을 활용해 팬텀 리드를 방지할 수 있다.

### 3-5. INNER JOIN과 OUTER JOIN
- 검수: [ ] (    )

INNER JOIN은 두 테이블에서 조인 조건을 만족하는 행만 결과로 반환한다. LEFT OUTER JOIN은 왼쪽 테이블의 모든 행을 반환하고, 오른쪽에 짝이 없으면 오른쪽 컬럼을 NULL로 채운다. RIGHT OUTER JOIN은 반대로 오른쪽 테이블의 모든 행을 반환한다. FULL OUTER JOIN은 양쪽 테이블의 모든 행을 반환하고 일치하는 행이 없으면 반대쪽 컬럼을 NULL로 채운다. MySQL은 FULL OUTER JOIN 문법을 직접 지원하지 않으므로 LEFT JOIN과 반대 방향의 조인 결과를 UNION 등으로 조합해 구현할 수 있다. 중복 행을 보존해야 하는 경우에는 UNION과 UNION ALL의 차이를 고려해야 한다.

### 3-6. DELETE, TRUNCATE, DROP의 차이
- 검수: [ ] (    )

DELETE는 DML로 행 단위로 삭제하며 WHERE로 조건을 줄 수 있고, InnoDB처럼 트랜잭션을 지원하는 스토리지 엔진에서는 트랜잭션 안에서 롤백할 수 있다. TRUNCATE는 DDL로 테이블 구조는 남기고 모든 행을 한꺼번에 지우며 WHERE를 쓸 수 없고 DELETE보다 빠르다. MySQL에서 TRUNCATE TABLE은 암묵적 커밋을 일으키는 DDL로, 일반적인 트랜잭션 롤백으로 되돌릴 수 없다. InnoDB에서는 테이블의 AUTO_INCREMENT 카운터도 초기화되며, 다른 테이블이 외래키로 참조하는 InnoDB 테이블은 TRUNCATE에 실패한다. DROP은 테이블 구조와 데이터를 포함해 테이블 자체를 삭제한다.

### 3-7. 키와 무결성
- 검수: [ ] (    )

기본키(PK)는 행을 유일하게 식별하는 키로 NULL과 중복이 허용되지 않는다. 외래키(FK)는 다른 테이블의 기본키(또는 유일 키)를 참조해 테이블 간 관계를 나타낸다. 개체 무결성은 기본키가 NULL이 아니고 유일해야 한다는 규칙이다. 참조 무결성은 외래키 값이 참조 대상에 존재하는 값이어야 한다는 규칙이며, 외래키 컬럼에 NULL을 허용하도록 정의한 경우에는 NULL이 될 수 있다. 도메인 무결성은 컬럼 값이 정의된 형식과 범위를 지켜야 한다는 규칙이다. 참조되는 행을 삭제·수정할 때는 CASCADE, SET NULL, RESTRICT 같은 옵션으로 동작을 정한다.

### 3-8. WHERE와 HAVING
- 검수: [ ] (    )

WHERE는 그룹화하기 전에 행 단위로 조건을 걸어 걸러내며 일반적으로 집계 결과를 조건으로 사용할 수 없다. HAVING은 그룹화된 결과에 조건을 적용하며 COUNT, SUM, AVG 같은 집계 함수를 사용할 수 있다. GROUP BY 없이 집계 결과 전체에 HAVING 조건을 적용하는 것도 가능하다. 실행 순서는 FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY다. GROUP BY는 지정한 컬럼 값이 같은 행을 하나의 그룹으로 묶어 집계할 수 있게 한다.

### 3-9. NoSQL
- 검수: [ ] (    )

관계형이 아닌 데이터베이스를 통틀어 부르는 말이다. 데이터 모델에 따라 키-값(Redis), 문서(MongoDB), 컬럼 패밀리(Cassandra), 그래프(Neo4j)로 나눈다. 스키마가 유연하고 수평 확장이 쉬운 제품이 많아 대용량·고성능 처리에 유리하다. 일부 NoSQL 제품은 관계형 DB보다 조인 기능이 제한적일 수 있으며, 트랜잭션 지원 수준은 제품마다 다르다. 일부 분산 NoSQL 데이터베이스는 가용성과 확장성을 중시하며 BASE(Basically Available, Soft state, Eventual consistency)와 같은 특성을 활용한다. 다만 NoSQL 전체가 BASE를 따르거나 일관성을 항상 양보하는 것은 아니며, 제품과 설정에 따라 일관성 보장 방식이 다르다.

### 3-10. 샤딩
- 검수: [ ] (    )

데이터를 여러 DB 서버에 나눠 저장하는 수평 분할 방식으로, 한 서버의 저장·처리 한계를 넘기 위해 쓴다. 샤드 키(예: 사용자 ID의 범위나 해시)로 데이터가 저장될 샤드를 정한다. 읽기·쓰기 부하와 데이터가 분산되는 장점이 있지만, 샤드 간 조인과 트랜잭션이 어렵고, 샤드 키를 잘못 고르면 특정 샤드에 데이터가 몰리며 재분배가 복잡하다. 같은 데이터를 복사해 읽기를 분산하고 가용성을 높이는 복제(replication)와는 다른 개념이다.

## 4. 자료구조·알고리즘 (category_id = 4)

### 4-1. 해시 테이블의 충돌 해결
- 검수: [ ] (    )

해시 테이블은 키를 해시 함수로 버킷 위치에 변환해 평균 O(1)에 저장·조회한다. 서로 다른 키가 같은 위치로 변환되는 것이 충돌이다. 해결 방법은 크게 두 가지다. 체이닝은 같은 버킷에 연결 리스트 등으로 여러 값을 잇고, 개방 주소법은 비어 있는 다른 버킷을 선형 탐색·이차 탐색·이중 해싱 등으로 찾는다. 충돌이 많으면 최악의 경우 O(n)까지 느려지므로 적재율이 높아지면 테이블 크기를 늘려 다시 해싱한다.

### 4-2. 스택과 큐
- 검수: [ ] (    )

스택은 나중에 들어온 것을 먼저 꺼내는 LIFO 구조로 `push`와 `pop`으로 조작한다. 함수 호출 스택, 되돌리기, 괄호 검사, DFS에 쓴다. 큐는 먼저 들어온 것을 먼저 꺼내는 FIFO 구조로 `enqueue`와 `dequeue`로 조작한다. 작업 대기열, 프린터 대기, BFS에 쓴다. 연결 리스트나 원형 배열 같은 일반적인 구현에서는 둘 다 삽입과 삭제가 O(1)이다. 배열 앞쪽 원소를 매번 이동시키는 큐 구현은 삭제가 O(n)이다.

### 4-3. 배열과 연결 리스트
- 검수: [ ] (    )

배열은 연속된 메모리에 저장되어 인덱스로 접근하면 O(1)이지만, 중간에 삽입·삭제하면 뒤의 원소를 이동해야 해서 O(n)이다. 일반 배열은 생성 시 크기가 정해지며, 동적 배열은 내부 배열을 재할당해 크기를 늘릴 수 있다. 연결 리스트는 노드가 포인터로 연결되어 특정 위치에 접근하려면 O(n)이 걸린다. 삽입·삭제할 노드와 필요한 선행 노드의 참조를 이미 알고 있다면 포인터 변경만으로 O(1)에 처리할 수 있지만, 위치를 먼저 탐색해야 한다면 탐색 비용 O(n)이 추가된다. 포인터를 저장하는 추가 메모리가 들고, 메모리가 흩어져 있어 캐시 효율이 배열보다 떨어진다.

### 4-4. 이진 탐색 트리
- 검수: [ ] (    )

각 노드의 왼쪽 서브트리 값은 노드보다 작고 오른쪽 서브트리 값은 노드보다 큰 이진 트리다. 탐색·삽입·삭제가 평균 O(log n)이지만 한쪽으로 치우친 경우(정렬된 순서로 삽입 등) 최악 O(n)이 된다. 중위 순회를 하면 값이 정렬된 순서로 나온다. 치우침을 막는 AVL 트리, 레드-블랙 트리 같은 균형 이진 트리는 O(log n)을 보장한다.

### 4-5. 퀵 정렬
- 검수: [ ] (    )

피벗을 하나 정해 피벗보다 작은 값과 큰 값으로 나눈 뒤, 각 부분을 재귀적으로 정렬하는 분할 정복 알고리즘이다. 평균 시간 복잡도는 O(n log n)이고, 피벗이 매번 최솟값이나 최댓값으로 잡히는 경우(이미 정렬된 입력 등) 최악 O(n²)이다. 일반적인 구현은 제자리 정렬에 가까워 배열 자체를 위한 추가 메모리가 적게 들지만, 재귀 스택 공간이 필요하다(평균 O(log n), 최악 O(n)). 같은 값의 상대적 순서가 바뀔 수 있는 불안정 정렬이다.

### 4-6. 다익스트라 알고리즘
- 검수: [ ] (    )

한 시작 정점에서 다른 모든 정점까지의 최단 거리를 구하는 알고리즘이다. 음수 가중치 간선이 없는 그래프에서만 쓸 수 있다. 아직 확정되지 않은 정점 중 거리가 가장 짧은 정점을 골라 확정하고, 그 정점을 거쳐 가는 경로로 이웃 정점의 거리를 갱신한다. 인접 리스트와 이진 힙 기반 우선순위 큐를 사용하면 일반적으로 O((V+E) log V) 시간에 동작한다. 모든 정점 쌍 사이의 최단 거리는 플로이드-워셜(O(V³))로 구한다.

### 4-7. 병합 정렬
- 검수: [ ] (    )

배열을 반으로 나누어 각각 정렬한 뒤, 정렬된 두 배열을 합치는 분할 정복 알고리즘이다. 입력과 무관하게 항상 O(n log n)이라 퀵 정렬과 달리 최악의 경우도 같다. 병합에 O(n)의 추가 메모리가 필요하고, 같은 값의 순서를 유지하는 안정 정렬이다. 연결 리스트 정렬이나 외부 정렬에 적합하다.

### 4-8. 이진 탐색
- 검수: [ ] (    )

정렬된 배열에서 가운데 값과 찾는 값을 비교해 탐색 범위를 절반씩 줄여 가는 알고리즘이다. 시간 복잡도는 O(log n)이다. 데이터가 정렬되어 있어야 하고, 인덱스로 임의 접근이 가능해야 하므로 정렬되지 않은 배열이나 연결 리스트에는 적합하지 않다. 반복문과 재귀 모두로 구현할 수 있다.

### 4-9. BFS와 DFS
- 검수: [ ] (    )

BFS(너비 우선 탐색)는 시작 정점에서 가까운 정점부터 한 단계씩 넓혀 가며 탐색하고 큐를 쓴다. 가중치가 없는 그래프에서 최단 경로를 구할 수 있다. DFS(깊이 우선 탐색)는 한 방향으로 끝까지 들어갔다가 되돌아오며 탐색하고 스택이나 재귀를 쓴다. 인접 리스트로 표현한 그래프에서 둘 다 O(V+E)이다. DFS는 사이클 탐지, 위상 정렬, 연결 요소 찾기에 자주 쓴다.

### 4-10. 힙과 우선순위 큐
- 검수: [ ] (    )

우선순위 큐는 우선순위가 가장 높은 원소를 먼저 꺼내는 자료구조이고, 보통 완전 이진 트리인 힙으로 구현한다. 최대 힙은 부모가 자식보다 크거나 같고, 최소 힙은 부모가 자식보다 작거나 같다. 원소 삽입과 루트 삭제(최댓값 또는 최솟값 추출)는 O(log n), 루트 조회는 O(1)이다. 배열로 구현할 수 있고 0부터 시작하는 인덱스 i의 자식은 2i+1, 2i+2번이다. 다익스트라 알고리즘, 작업 스케줄링, 힙 정렬에 쓴다.

## 5. 객체지향·웹 (category_id = 5)

### 5-1. 쿠키와 세션
- 검수: [ ] (    )

HTTP는 요청 사이의 상태를 기억하지 않으므로 로그인 같은 상태 유지를 위해 쿠키와 세션을 쓴다. 쿠키는 서버가 `Set-Cookie`로 내려 준 데이터를 브라우저가 저장하고 조건에 맞는 이후 요청에 자동으로 보내는 방식이다. 클라이언트에 저장되므로 사용자가 값을 확인·변경할 수 있어 민감한 정보를 그대로 저장해서는 안 된다. 세션은 일반적으로 상태를 서버 측에 저장하고 클라이언트에는 세션 ID를 쿠키로 전달한다. 세션 ID 보호, 쿠키의 Secure·HttpOnly·SameSite 설정 등 보안 설정이 중요하며, 서버가 여러 대라면 세션 공유 저장소(예: Redis)가 필요할 수 있다.

### 5-2. 객체지향의 4가지 특징
- 검수: [ ] (    )

캡슐화는 데이터와 그것을 다루는 메서드를 하나로 묶고 접근 제어로 내부를 숨기는 것이다. 상속은 상위 클래스의 속성과 기능을 하위 클래스가 물려받아 재사용하는 것이다. 다형성은 같은 인터페이스나 상위 타입으로 서로 다른 구체 타입의 객체를 다루고, 실제 객체의 구현에 따라 동작이 달라질 수 있는 성질이다. Java에서는 메서드 오버라이딩과 인터페이스 등을 통해 런타임 다형성을 구현한다. 추상화는 공통되고 핵심적인 부분만 모델링하고 불필요한 세부는 숨기는 것으로 추상 클래스와 인터페이스로 표현한다.

### 5-3. SOLID 원칙
- 검수: [ ] (    )

객체지향 설계의 다섯 원칙이다. SRP(단일 책임)는 클래스가 하나의 변경 이유만 갖도록 설계하는 것, OCP(개방-폐쇄)는 확장에는 열려 있고 수정에는 닫혀 있는 것, LSP(리스코프 치환)는 하위 타입이 상위 타입을 대체해도 동작이 올바른 것, ISP(인터페이스 분리)는 클라이언트가 쓰지 않는 메서드에 의존하지 않도록 인터페이스를 작게 나누는 것, DIP(의존 역전)는 고수준 모듈이 저수준 구현이 아니라 추상화에 의존하는 것이다.

### 5-4. 인터페이스와 추상 클래스
- 검수: [ ] (    )

추상 클래스는 필드와 생성자, 구현된 메서드를 가질 수 있고 단일 상속만 가능하며, 관련된 클래스들이 공통 상태와 코드를 공유하는 is-a 관계에 쓴다. 인터페이스는 구현 클래스가 지켜야 할 역할(계약)을 정의하고 여러 개를 동시에 구현할 수 있다. Java 8부터 `default`와 `static` 메서드를 선언할 수 있고, Java 9부터 `private` 메서드(정적 메서드 포함)도 선언할 수 있다. 인스턴스 필드는 가질 수 없으며 인터페이스에 선언한 필드는 암묵적으로 `public static final` 상수다.

### 5-5. REST
- 검수: [ ] (    )

자원을 URI로 표현하고 그 자원에 대한 행위를 HTTP 메서드(GET, POST, PUT, PATCH, DELETE)로 나타내는 아키텍처 스타일이다. 클라이언트-서버 분리, 무상태, 캐시 가능, 균일한 인터페이스, 계층화 같은 제약을 따른다. URI에는 행위가 아니라 자원(명사)을 쓴다. GET은 안전하고 멱등하며, PUT과 DELETE는 멱등하고, POST는 멱등하지 않다. PATCH는 수행하는 변경에 따라 멱등 여부가 달라진다.

### 5-6. DI와 IoC
- 검수: [ ] (    )

IoC(제어의 역전)는 객체의 생성과 의존 관계 설정을 개발자가 아니라 컨테이너나 프레임워크가 맡는 설계 원칙이다. DI(의존성 주입)는 필요한 의존 객체를 클래스 내부에서 만들지 않고 외부에서 넣어 주는 방식으로 IoC를 구현하는 방법이다. 생성자 주입, 세터 주입, 필드 주입이 있고, 생성자 주입이 불변성과 테스트 용이성 때문에 권장된다. 결합도가 낮아지고 Mock 객체로 대체해 테스트하기 쉬워진다. Spring은 ApplicationContext가 빈을 만들고 연결한다.

### 5-7. 오버로딩과 오버라이딩
- 검수: [ ] (    )

오버로딩은 같은 클래스(또는 상속 관계 등 허용되는 범위)에서 이름이 같고 매개변수 목록이 다른 메서드를 여러 개 정의하는 것이다. 컴파일 시점에 호출할 메서드가 정해지고(정적 바인딩), 반환 타입만 다른 것은 오버로딩이 아니다. 오버라이딩은 하위 클래스가 상위 클래스의 메서드를 같은 시그니처로 다시 정의하는 것이다. 실행 시점에 실제 객체 타입에 따라 호출될 메서드가 정해지는(동적 바인딩) 다형성의 기반이다. `final` 메서드는 오버라이딩할 수 없고, `private` 메서드는 하위 클래스에서 상속되지 않으므로 오버라이딩 대상이 아니다. 오버라이딩할 때는 상위 메서드보다 접근 범위를 좁힐 수 없다. 정적 메서드는 인스턴스 메서드처럼 오버라이딩되지 않고 메서드 숨김(method hiding)이 발생한다.

### 5-8. String, StringBuilder, StringBuffer
- 검수: [ ] (    )

String은 불변 객체라 기존 문자열을 변경하는 연산은 새로운 문자열 객체를 만들 수 있다. 반복문에서 문자열을 계속 연결하면 중간 객체가 많이 생성될 수 있으므로, 반복적인 변경에는 StringBuilder를 사용하는 것이 일반적이다. 다만 컴파일러가 최적화하는 단순한 연결식의 성능은 실행 환경에 따라 달라질 수 있다. StringBuilder는 가변이며 동기화를 하지 않아 단일 스레드에서 빠르다. StringBuffer는 가변이며 메서드가 동기화되어 스레드에 안전하지만 더 느리다. String이 불변이라 문자열 상수 풀에서 공유할 수 있고 해시 값을 캐시할 수 있으며 스레드에 안전하다.

### 5-9. XSS와 CSRF
- 검수: [ ] (    )

XSS는 공격자가 악성 스크립트를 사이트에 심어 다른 사용자의 브라우저에서 실행되게 하는 공격으로, 쿠키·세션 탈취 등으로 이어진다. XSS는 출력 문맥에 맞는 이스케이프, 안전한 DOM 처리(`innerHTML` 대신 `textContent` 등), CSP(Content Security Policy) 등으로 예방한다. HttpOnly 쿠키는 XSS가 발생했을 때 JavaScript의 `document.cookie`를 통한 쿠키 탈취 위험을 줄여 주는 보조 수단이며, XSS 자체를 차단하거나 XSS 스크립트가 인증된 요청을 보내는 것을 막지는 못한다. CSRF는 로그인된 사용자의 브라우저가 사용자 의도와 무관하게 공격자가 만든 요청을 인증 정보(쿠키)와 함께 서버에 보내게 하는 공격이다. CSRF 토큰, SameSite 쿠키, Origin·Referer 검증으로 막으며, SameSite를 지정하지 않은 쿠키는 Chromium 계열 브라우저에서 기본적으로 Lax로 취급하지만 다른 브라우저는 다를 수 있으므로 명시적으로 지정하는 것이 안전하다. XSS는 사용자가 사이트를 믿는 점을, CSRF는 사이트가 사용자의 브라우저를 믿는 점을 악용한다.

### 5-10. SQL Injection
- 검수: [ ] (    )

사용자 입력이 SQL 문의 일부로 해석되도록 조작해 의도하지 않은 쿼리를 실행시키는 공격이다. SQL을 문자열 결합으로 만드는 로그인 기능에서는 입력값 조작으로 인증을 우회할 수 있다. 데이터 유출·변조·삭제로 이어질 수 있다. PreparedStatement 같은 파라미터 바인딩으로 입력을 값으로만 처리하는 것이 기본 방어다. 테이블명·컬럼명·정렬 방향처럼 바인딩할 수 없는 SQL 식별자를 동적으로 구성할 때는 허용 목록으로 검증해야 한다. JPA 같은 ORM도 바인딩을 쓰지만 네이티브 쿼리를 문자열로 이어 붙이면 위험하다. 입력 검증, DB 계정 최소 권한, 상세 오류 메시지 숨김도 함께 적용한다.
