# STT 재연결 시 밀린 발언 저장 부하 테스트

여러 강사가 동시에 연결을 복구했을 때 발언 한 건을 저장하는 시간과, 방마다 밀린 발언을 전부 저장하는 시간을 측정한다. 각 가상 사용자는 한 방의 강사다. 서로 다른 방에서는 동시에 전송하고, 한 방에서는 앞선 요청의 응답을 받은 뒤 다음 발언을 보낸다.

## 실행

Docker 엔진을 켜고 JDK 25, Python 3.10 이상, k6가 준비된 환경에서 저장소 루트에서 실행한다.

```powershell
python infra/k6/stt_load.py 40
```

숫자 하나로 동시에 재연결할 방 수를 바꾼다. 기본값은 전송 중단 10초, 방당 밀린 확정 발언 20건이다. 위 명령에서는 재연결 후 새 발언 800건을 저장한다. 전송 전의 기준 발언과 응답 유실을 가정한 동일 요청 재시도는 별도로 보낸다. 전송 중단 시간과 발언 수도 조정할 수 있다.

```powershell
python infra/k6/stt_load.py 40 --offline-seconds 30 --backlog 50
```

실행기가 테스트 전용 MySQL·Redis와 백엔드를 띄우고, 서로 다른 강사 계정으로 로그인해 강연방과 STT 녹음 세션을 준비한다. 로그인과 방 준비는 측정 전에 끝낸다. 실제 음성 대신 k6가 확정 전사 텍스트를 만들고, 전송을 보류해 네트워크 단절을 모의한다.

## 측정과 검증

1. 전송 중단 전에 방을 하나씩 돌며 기준 발언을 한 건씩 저장한다. 모든 방의 저장이 끝나면 공통 전송 중단 구간이 시작된다. 이 구간의 발언에는 원래 발언 시각과 고유 키를 붙인다.
2. 공통 재연결 시각이 되면 각 강사가 로그인 계정을 확인하고 밀린 발언을 순서대로 보낸다. 첫 발언은 응답 유실을 가정해 같은 내용과 키로 다시 보내고, 서버가 최초 발언 ID와 최초 수신 시각을 그대로 반환하는지 확인한다.
3. 모든 방의 측정이 끝나면 한 방에서 음성 인식 오류로 누락 구간을 열고, 마지막 발언 저장과 강연 종료를 동시에 요청한다. 저장이 먼저 처리되면 한 건이 남고, 종료가 먼저면 새 저장은 거절되어야 한다. 종료 시 열린 누락 구간이 닫히고 이미 저장한 발언의 재전송은 기존 ID를 반환하는지도 확인한다. 이 검증은 위 지연 통계에서 제외한다.
4. MySQL에서 방·세션별 발언의 키, 본문, 시각과 건수를 대조한다. 누락·중복·다른 방 기록의 혼입이나 예상하지 않은 API 응답이 있으면 명령이 실패한다. 검증 후 실행기가 전용 서비스를 정리한다.

## 결과 읽기

실행 결과는 `backend/build/reports/stt-reconnect/<run-id>/`에 남는다. 먼저 k6와 DB 검증이 모두 통과했는지 확인한 뒤 지연을 비교한다.

| 확인할 값 | 의미 |
| --- | --- |
| `k6-summary.json` → `stt_segment_save_ms` | 재연결 후 새 발언 한 건을 저장하는 HTTP 요청의 지연. `p(95)`, `p(99)`는 밀리초 단위다. `stt_live_save_ms`는 전송 중단 전에 방별로 한 건씩 보낸 요청의 지연이다. |
| `k6-summary.json` → `stt_backlog_drain_ms` | 한 방이 재연결한 뒤 계정 확인과 재시도를 거쳐 마지막 저장 응답까지 받은 시간. 가장 늦게 끝난 방은 `max`로 확인한다. |
| `k6-summary.json` → `stt_reconnect_offset_ms` | 예정된 공통 재연결 시각에서 실제로 각 방이 전송을 재개하기까지의 차이. 방 수를 늘렸을 때 재연결이 얼마나 퍼졌는지 보여 준다. |
| `db-verification.json` | `verified`가 선택한 방 수와 같고 `failures`가 비어 있으면 모든 방의 저장 결과가 검증된 것이다. 기본 40개 방에서는 기준 40건과 밀린 발언 800건을 합한 840건이 필수이며, 종료와 동시에 보낸 1건은 처리 순서에 따라 추가된다. |
| `run.json`, `k6.log`, `backend.log` | 각각 실행 조건, 실패한 k6 검사, 서버 로그를 확인한다. |

기존 로컬 모니터링의 Prometheus가 remote write를 수신 중이면 같은 명령이 실행 지표도 전송한다. [Grafana Explore](http://localhost:3000/explore)에서 데이터 소스 **RE:ACT Prometheus**를 선택하고 아래 쿼리의 `RUN_ID`를 실행기에 표시된 값으로 바꾼다. 방별 완료 시간은 해당 방의 큐가 모두 비워지면 표시된다.

```promql
k6_stt_backlog_drain_ms_p95{run_id="RUN_ID"}
```
